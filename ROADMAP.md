# Roadmap

New functionality not yet started. Bugs, gaps and follow-ups to existing features are tracked as [GitHub issues](https://github.com/alslater/package-alert/issues).

## Planned
- [ ] Cooldown violations reported to pa-central, with server-managed allowlist synced back — pending pa-central server support (no API for this yet). On block, `CentralPlugin` enqueues the violation (ecosystem, package, version, age, risk score, reason) to `central_outbox` for later drain — fire-and-forget, no wait for clearance, the install continues either way. A central user reviews violations and sets an allowlist entry server-side; pa pulls the updated allowlist down (daemon-driven, plus an on-demand `pa central sync` command) and merges it into local cooldown clearance. Since pa-central is only useful with the daemon running, outbox drain and allowlist sync both piggyback on the existing daemon lifecycle.
- [ ] Typosquat signal: edit-shape classification — `TyposquatDetector` currently scores by edit *count* (Levenshtein distance) and discards what kind of edit it was. Attacks use a small set of recognisable shapes: character transposition (`reqeusts` ← `requests`), single-character omission (`urlib3`), doubling (`requestss`), keyboard-adjacent substitution (`rewuests`), and homoglyph substitution (`rn`→`m`, `l`→`1`, `0`→`o`, Cyrillic lookalikes). Appending or altering a meaningful token is not an attack shape. Weighting the score by edit *type* rather than edit count would let the detector keep full distance-2 coverage while suppressing the remaining benign collisions, and would catch homoglyph attacks that current normalisation (`[-_.]+` → `-`, lowercase) does not address at all. Implement as a classifier returning an attack-shape confidence that multiplies the base score, alongside the existing adoption and version-suffix adjustments.
- [ ] Typosquat signal: registry age of the suspect — a name-similar package that has existed for years is not an active attack. `publication_date_url` and `fetch_publication_date` already exist for the cooldown policy and the age damper, so the data is available and cached; wire the *first* release date (not the current version's) into the typosquat score as a third corroborating reduction. Weaker evidence than adoption, since an attacker can register a name and wait, so it should contribute less weight than `dependent_count` and never on its own.
- [ ] Typosquat signal: shared-maintainer detection — `httpx`, `httpcore`, and `respx` are all published by the same organisation, which is conclusive evidence that a name resemblance is a package family rather than a squat. This is the most semantically correct suppression signal available, and the only *automatic* one that would let a version-suffixed release line be recognised as legitimate before it has accrued dependents — currently such a package is gated until adoption corroborates it, which is the safe default but does produce a false positive for a genuine new major release. Note the per-signal package allowlist (`--signal typosquat`) covers the same false positive manually and at far lower cost, so this item is worth doing for automatic coverage, not as a prerequisite. Requires a new `LanguageBase` hook (`maintainer_url(name)` plus a parse method) because each registry exposes ownership differently: PyPI has no maintainer field in the JSON API and needs the `/pypi/<pkg>/json` `info.author`/`maintainer` fields or a scrape, npm has `maintainers[]` in the registry document, and Packagist has vendor namespacing that makes it nearly free. Cache per package alongside the popularity data. Treat a maintainer match as a strong reduction but not a veto, since an attacker could publish under a plausible-looking account name.
- [ ] poetry + pdm support
- [ ] `pa fix` for the other package managers. `pa fix` plans and verifies remediation for uv projects (`uv.lock`) and npm projects (`package-lock.json`, done: direct pins, parent upgrades and range-scoped `overrides` as forced pins, trialled with `npm install --package-lock-only` in a scratch copy; the adapter is in `packagealert/languages/node_fix/`). It picks one recommended version per vulnerable package and checks each pin with a sandboxed trial, holding back pins that are blocked, would downgrade, would add advisories, or need a major upgrade or a version still in cooldown. A language plugin supplies adapters through the optional `fix_adapters()` hook (`packagealert/remediate/adapter.py`, documented in LANGUAGES.md), so a new manager is a new adapter; the plugin also declares which of that manager's commands the sandbox may run, through `is_read_only_command()` (read-only, in the project) or `is_scratch_command()` (writing, in a scratch copy). Still to do: requirements files (pip), `Pipfile.lock` (pipenv), `yarn.lock`, `pnpm-lock.yaml`, `composer.lock`, and for npm, workspaces and `npm-shrinkwrap.json`. Each one is an adapter behind the same interface:
  - **Graph:** load the lock file's dependency graph, with workspace members, direct dependencies and dependency edges. The existing lockfile parsers build part of this and discard the edges.
  - **Commands:** turn a plan into the manager's own exact-pin commands.
  - **Trial:** run a trial resolve in the sandbox (read-only, or in a scratch copy) and parse its result fail-closed into resolved, blocked or inconclusive, with its list of changes.

  The verification policy in `remediate/verify.py` stays the same for every manager: the parent retry, the exact-pin confirmation, the combined trial, and the major and cooldown checks.

  First establish whether each manager has a resolve that writes nothing, and measure how its output can be parsed. Possible starting points, none of them yet verified for this purpose: `pip install --dry-run --report`; `pnpm install --lockfile-only`; `composer update --dry-run` with `--with pkg:ver`; and `pipenv lock` (also in a scratch copy).

  Where only a lock-writing resolve exists, trial it against a copy of the project, never in place. Requirements files are a different case: a fix there is an edit to the pin, not a lock update, and transitive packages are often unpinned.

  Record each manager's trial output in fixtures under `tests/fixtures/`, as `tests/fixtures/uv_trial/` and `tests/fixtures/npm_trial/` do, and re-record them when that manager is audited.
- [ ] EPSS-weighted advisory severity — `advisories.ecosyste.ms`'s `/advisories/lookup?purl=...` endpoint returns, alongside CVSS, an `epss_percentage`/`epss_percentile` (exploit prediction score) and a `blast_radius` figure that OSV does not provide. Discovered while auditing the npm top-packages corpus — a separate ecosyste.ms sub-service from the `packages.ecosyste.ms` one used there, aggregating advisories from GHSA, CPANSA, Erlef, and others, deduplicated by CVE. Not a replacement for the existing `OsvClient`/`osv_cache` path (`packagealert/osv/client.py`), which already federates GHSA/PYSEC/etc. through OSV and has its own tuned CVSS-vector parsing — likely high overlap in raw advisory coverage. The distinct value is EPSS: an advisory's CVSS severity says how bad exploitation would be, EPSS says how likely exploitation actually is in the near term, and the two are commonly combined for prioritisation. Evaluate folding EPSS into the composite risk score (or surfacing it as a separate `RiskSignal`) for packages that already have an OSV-sourced vulnerability, rather than switching advisory sources outright.
- [ ] macOS support (sandbox alternative to bwrap, macOS desktop notifications, Homebrew; platform-specific cache paths e.g. `~/Library/Caches/pip`; cache monitoring already works via watchdog's FSEvents backend)
- [ ] Windows support (ReadDirectoryChangesW)
- [ ] Obfuscated code detection — flag packages containing heavily obfuscated source: `eval`/`exec` of base64-decoded or hex-encoded payloads, high-entropy string literals, single-line minified scripts used as install hooks, and similar patterns seen in supply chain attacks (inspired by Socket.io's obfuscation checks). Contribute as a heuristic signal to the existing risk scoring engine.
- [ ] YARA rule integration for binary inspection
- [ ] Webhook / Slack alert channel
- [ ] Lightweight local web dashboard
- [ ] CI integration (GitHub Actions action, GitLab CI component, Bitbucket Pipelines pipe)
- [ ] Alert detail view — `pa alerts show <id>` (or `pa alerts` row expansion) showing the full risk signal breakdown: individual signal names, scores, and reasons (typosquat match, low popularity, install script, embedded binary, etc.) that contributed to the composite score. The alerts table currently shows only the total score, giving no actionable information about why a package was flagged.
- [ ] Alert management — `pa alerts delete <id>` and `pa alerts clear` (with optional `--before <date>`, `--ecosystem`, `--risk-only` / `--advisory-only` filters) to remove stale or false-positive entries from the database. Currently there is no way to clean up alerts without directly editing the SQLite database.
- [ ] Package allowlist — `pa allowlist add <package> [--ecosystem] [--version] [--reason]` to permanently suppress alerts for known-safe or in-house packages. Two distinct use cases: (1) internal packages hosted on a private registry that will always trigger low-popularity signals; (2) packages that have been manually reviewed and determined safe despite heuristic signals. Allowlist entries should be scoped (per-project or global), stored in config or the database, and visible in `pa allowlist list`. Allowlisted packages should be skipped by the daemon, pre-flight check, and post-install scan — not just suppressed at alert display time. Model the storage and CLI on the existing `cooldown_cleared` table and `pa cooldown allow` command, which already solve the same shape of problem (a user-granted, persisted, per-package exemption) — and subsume that command's surface, per "Subsuming `pa cooldown allow`" below.

  **Per-signal suppression.** A blanket allowlist is too coarse to be the only option: suppressing everything for a package also suppresses genuine OSV advisories and install-script signals that appear in a later version. Support `--signal <name>` (repeatable) to waive named signals only — `pa allowlist add somepkg2 --signal typosquat --reason "genuine v2 release line"` — leaving every other signal active. A bare `pa allowlist add` with no `--signal` remains the full-suppression form for genuinely trusted in-house packages. Waiving a signal should subtract it from the composite score rather than zeroing the report, so the remaining signals still gate normally; `pa allowlist list` must show which signals each entry waives, and `scan-project --details` should mark a suppressed signal as waived rather than hiding it, so a suppression can never silently outlive its justification.

  This is the practical answer to the false positive left by adoption-corroborated typosquat scoring: a genuine new major release such as `somepkg2` is gated until it accrues dependents, and `--signal typosquat` lets a maintainer or user clear exactly that one objection for exactly that one package without weakening anything else. It is a better fit for this case than shared-maintainer detection below, because it needs no per-registry ownership plumbing and expresses a decision the user has actually made. Consider `--expires <duration>` for the specific case of waiving a typosquat objection on a package expected to accrue adoption, so a temporary exemption does not become permanent by default.

  **Subsuming `pa cooldown allow`.** `pa cooldown allow <pkg> <ver>` already implements a user-granted, persisted, per-package exemption, so having two commands for "waive this objection" is one too many. Fold the *surface* into this feature — `pa allowlist add <pkg> --version <ver> --signal cooldown` — and have `pa allowlist list` show cooldown clearances alongside signal waivers, so users learn one command and can see every active exemption in one place. Keep `pa cooldown allow` as a documented alias rather than removing it: it appears in the README quick start and in agent workflows, and the pre-clearance path is load-bearing for unattended installs.

  Fold the surface, **not** the mechanism. Cooldown is not a risk signal and must not be modelled as one:

  - It contributes no score. Signals are `RiskSignal(name, score, reason)` summed into a composite, so a waiver subtracts a number; cooldown returns a `CooldownDecision` action directly, with nothing to subtract. `--signal cooldown` must route to `cooldown_cleared` (the existing storage, with its `cleared_at` semantics), not to score arithmetic.
  - It is version-specific and self-expiring — an objection to `foo==1.2.3` is moot after `period_days`, and clearances already expire on the same window. A typosquat objection attaches to a *name* and never expires on its own. So `--version` stays optional for signal waivers but is required for `--signal cooldown`, and `--expires` is meaningful for typosquat while cooldown keeps its existing implicit expiry.
  - The two must remain independently configurable. `pa run` deliberately evaluates the risk gate *before* the cooldown check, and the risk gate exists to catch things cooldown cannot (a typosquat on an old package). Collapsing them into one waiver would let clearing a cooldown prompt silently also clear a typosquat block, which is precisely the coupling the Phase 3 work removed.
- [ ] `pa install-git-hooks` — a gap in the current enforcement model: `uv lock` (and equivalent fresh-resolve commands in other ecosystems) is deliberately ungated — see `subcmd == "lock"` in `parsers/process_args.py`, which resolves a full dependency graph from `pyproject.toml` without checking any resulting package, transitive or direct, because the existing `uv.lock` it would otherwise scan is stale and about to be replaced. That is the right call for `uv lock` in isolation, but it means a lock file can be produced, on any machine, containing a package that would be blocked the moment someone actually ran `pa run uv sync` against it — and nothing stops that lock file from being `git add`ed and committed in the meantime. All of package-alert's enforcement today sits at the package-manager-invocation boundary (`pa run`, shell/project shims); nothing sits at the git boundary, so a bad lock file can reach a shared branch, CI, or a teammate whose local policy is laxer (`on_new_low_risk = "warn"`) or who runs bare `uv sync` outside `pa run` entirely, before local enforcement ever gets a chance to catch it.

  A `pre-commit` hook that runs the equivalent of a targeted `pa scan-project` against staged lock files and exits non-zero on a blocking finding closes this: even a lock file produced by an ungated resolve, or written on a machine with no shims/daemon running, gets caught at the one point every workflow funnels through. It must reuse the exact same decision path `pa run` uses (`decide_with_cleared` / `cooldown_cleared`, synced from pa-central where configured — see the cooldown-violations item above) rather than a second, independently-tuned policy: a hook that reflags something a fleet admin already cleared centrally would train people to `git commit --no-verify` past it, which is worse than no hook at all.

  This only closes half the gap. `.git/hooks/` is not version-controlled, so cloning the repo does not install the hook — installing it has to be a step someone (or an onboarding script) actually runs, which is why this needs to be a command rather than a checked-in file. Two install strategies, not mutually exclusive: (1) write directly to `.git/hooks/pre-commit` — simple, matches the common mental model, but per-clone and invisible to code review; (2) write hook content to a repo-tracked directory (e.g. `.githooks/`) and set `core.hooksPath` to it — the hook itself becomes reviewable and shareable in PRs, but still requires the one-time `git config core.hooksPath .githooks` per clone, so it is not truly automatic either way. Lean toward (2) as the default with (1) as a `--local` fallback for a dev who does not want a repo-wide git config change. Whether an org *requires* the hook to be installed (mandatory onboarding step, CI double-check that `core.hooksPath` is set, branch protection) is a policy decision for that org, not something this tool enforces — package-alert's job is to make the mechanism correct and easy to install, not to guarantee it is.
- [ ] Configuration safety audit — scan the loaded config for common misconfigurations (overly broad `editable_roots`, credential paths in `extra_ro_paths`, etc.) and warn at startup
- [ ] IDE/tool install policy — detect and surface package installations triggered by background processes (VS Code extensions, language servers, IDEs) using parent process chain; optionally block or require explicit approval for non-user-initiated installs
- [ ] `pa config upgrade` command — append missing config keys (commented, with defaults) to the installed config file after an upgrade, so users are not silently missing new options; `--dry-run` prints a diff without writing
