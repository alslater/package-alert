## Phase 3 (Planned)
- [x] yarn + pnpm process monitoring, lockfile parsing, and lockfile-hint deferred scanning
- [x] Shadow tools: shell function integration (`setup shell`) and project-local shims (`setup project`) for transparent interception of pip, npm, uv, etc. — including `python -m pip` via interpreter-aware shims
- [x] Cooldown policy: block/prompt/warn/allow installs of recently-published packages; per-project config; `cooldown allow` for agent pre-clearance
- [x] Popularity-weighted heuristic dampening — deps.dev `dependent_count` and `version_count` are fetched and cached; heuristic signal scores are multiplied by a `popularity_factor` that scales from 1.0 (obscure) down to a configurable `popularity_floor` (default 0.25) at `high_dependent_count` (default 1000). Scoped npm package names are percent-encoded. Transient fetch failures write a short-lived sentinel and produce a warning rather than manufacturing false signals; genuine 404s are silent and neutral.
- [x] Version age dampening — publication date is fetched from the registry and cached; an `age_factor` scales from 1.0 (newly published) down to `age_floor` (default 0.25) at `max_damping_age_days` (default 90). The two factors are combined (product, floored at `combined_damping_floor`) and applied to all heuristic signals except `low_popularity` and `typosquat`.
- [x] Score–signal consistency — the final score is computed as `floor(Σ(score × factor))` (single floor after summing fractional products, per spec). Displayed per-signal scores are reconciled to the same total using the largest-remainder method so `sum(signal.score) == report.score` in all cases, including when the 100-cap bites.
- [x] Third-party plugin popularity ecosystem support — `popularity_ecosystem()` hook on `LanguageBase`; registry builds the `PopularityClient` ecosystem map from all registered plugins; covered by a `DistributionFinder`-based integration test.
- [x] Batch deduplication fixed — co-arriving events are deduplicated by `(ecosystem, package, version, project_path)` so two different projects installing the same package version in the same drain window each receive their own alert.
- [x] Typosquatting and heuristic risk scoring in `scan-project` output and `pa run` pre-flight — `scan-project` scores every queried lock file package by default (bounded to 10 concurrent deps.dev calls, `--no-risk` to opt out) and renders a risk section in text, JSON, and HTML; per-package failures degrade to "no score" and never fail the scan. `pa run` gained a risk gate (`[sandbox.preflight_risk]`) that runs *before* the cooldown check and warns/prompts/blocks on typosquat matches and scores at or above `risk_threshold`, independently of the cooldown policy. This fixed two coverage holes where typosquat detection was silently skipped: for ecosystems whose language module returns no `publication_date_url` (Packagist had no typosquat detection at all), and for unpinned packages whose latest version could not be resolved. Typosquat false positives are handled by corroborating signals rather than by narrowing the distance threshold: the risk engine scales the typosquat score down by the suspect package's own `dependent_count` (reusing the already-fetched deps.dev data, floored so a finding is never silenced). A trailing version digit (`httpx2`, `psycopg2`) deepens that reduction but is never sufficient on its own — `TyposquatDetector` reports the observation without acting on it, because the same name shape fits both a genuine successor release line and a brand-new squat, and treating it as exculpatory would make appending a digit a one-character bypass. Gating keys on the resulting score (`typosquat_min_score`, default 15) rather than the bare match, so `httpx2` (18,689 dependents) is allowed while `reqeusts`, `requests2`, and `numpy2` (all absent from deps.dev) keep their full score and are gated — and `typosquat_max_distance` stays at 2, preserving genuine distance-2 attacks like `cryptografy`. The cooldown check now receives the composite `RiskEngine` score rather than the typosquat score alone. The sandboxed-shell path is gated on the same policy, with the highest-ranked action across all scored lock file packages governing the decision. Known remaining false positive: a genuine new major release (`somepkg2`) is gated until it accrues dependents — to be addressed by the per-signal package allowlist (`--signal typosquat`) below. `_post_scan` additionally scores newly installed packages with a real `package_dir`, so install-script, `eval`, and embedded-binary signals gate the existing snapshot rollback via `on_post_install_risk`. `scan-project --scan-installed` also gets the full source-code heuristics: that mode enumerates packages from a real venv/`site-packages` or `node_modules`, so `score_packages` takes an optional `package_dir_resolver` and the pass supplies one only in that mode — a package with a malicious `setup.py` scores 80 (`critical`) where metadata alone scored 0. Because source signals raise the range, `_preflight_level` uses `post_install_threshold` (30) as the `warning` boundary for `--scan-installed` and `risk_threshold` (25) for lock-file scans. Resolver failures degrade a package to metadata-only rather than counting as a scoring failure.
- [ ] Cooldown violations reported to pa-central, with server-managed allowlist synced back — pending pa-central server support (no API for this yet). On block, `CentralPlugin` enqueues the violation (ecosystem, package, version, age, risk score, reason) to `central_outbox` for later drain — fire-and-forget, no wait for clearance, the install continues either way. A central user reviews violations and sets an allowlist entry server-side; pa pulls the updated allowlist down (daemon-driven, plus an on-demand `pa central sync` command) and merges it into local cooldown clearance. Since pa-central is only useful with the daemon running, outbox drain and allowlist sync both piggyback on the existing daemon lifecycle.
- [ ] Complete the `LANGUAGES.md` contract reference — eight `LanguageBase` methods are missing from the guide's method list despite being part of the contract: `parse_package_spec`, `serialise_package_spec`, `cache_file_globs`, `available_flags`, `popularity_ecosystem`, `configure_sandbox_writable_warning`, `detect_new_packages`, `home_ro_paths`. Some appear only in the version changelog, others nowhere at all, so a plugin author reading the reference implements an incomplete module and loses the corresponding capability silently — the same failure mode as the v5 hooks that were missing until the signature drift was reported. Document each with its signature, when it is called, and what degrades if omitted, then widen `test_guide_documents_every_v5_contract_method` (`tests/unit/test_sandbox.py`) from the v5 subset to the whole protocol so the reference cannot drift again.
- [ ] Interpreter-mediated invocation as a plugin capability — `parsers/process_args.py` dispatches on executable names (`python`, `python3`, `php`, `php8`, `node`, `nodejs`) to recognise invocations where a package manager is run *through* an interpreter: `python -m pip install`, `php composer.phar require`, `node npm-cli.js`. These literals sit before any ecosystem is known, so they are a different category from the ecosystem conditionals removed in the v5 contract (see `docs/superpowers/specs/2026-08-12-ecosystem-conditional-removal-design.md`), but they are the remaining reason adding a language can require editing a core parser. `package_manager_names()` and `interpreter_names()` already cover direct invocation and interpreter shimming; what is missing is a way for a plugin to declare *interpreter + script* patterns, so a hypothetical Ruby module cannot register `ruby gem.rb`-style entry points. Extend the contract with something like `interpreter_invocations() -> list[tuple[str, str]]` (interpreter name, script-name substring) and drive the parser from the registry. Deferred because it touches process monitoring rather than the plugin-visible scoring path, so the regression risk is higher and the benefit narrower. Doing this also unblocks a guard test that fails CI on any new ecosystem literal outside `packagealert/languages/` — currently impractical because such a grep false-positives on these command names.
- [ ] Typosquat signal: edit-shape classification — `TyposquatDetector` currently scores by edit *count* (Levenshtein distance) and discards what kind of edit it was. Attacks use a small set of recognisable shapes: character transposition (`reqeusts` ← `requests`), single-character omission (`urlib3`), doubling (`requestss`), keyboard-adjacent substitution (`rewuests`), and homoglyph substitution (`rn`→`m`, `l`→`1`, `0`→`o`, Cyrillic lookalikes). Appending or altering a meaningful token is not an attack shape. Weighting the score by edit *type* rather than edit count would let the detector keep full distance-2 coverage while suppressing the remaining benign collisions, and would catch homoglyph attacks that current normalisation (`[-_.]+` → `-`, lowercase) does not address at all. Implement as a classifier returning an attack-shape confidence that multiplies the base score, alongside the existing adoption and version-suffix adjustments.
- [ ] Typosquat signal: registry age of the suspect — a name-similar package that has existed for years is not an active attack. `publication_date_url` and `fetch_publication_date` already exist for the cooldown policy and the age damper, so the data is available and cached; wire the *first* release date (not the current version's) into the typosquat score as a third corroborating reduction. Weaker evidence than adoption, since an attacker can register a name and wait, so it should contribute less weight than `dependent_count` and never on its own.
- [ ] Typosquat signal: shared-maintainer detection — `httpx`, `httpcore`, and `respx` are all published by the same organisation, which is conclusive evidence that a name resemblance is a package family rather than a squat. This is the most semantically correct suppression signal available, and the only *automatic* one that would let a version-suffixed release line be recognised as legitimate before it has accrued dependents — currently such a package is gated until adoption corroborates it, which is the safe default but does produce a false positive for a genuine new major release. Note the per-signal package allowlist (`--signal typosquat`) covers the same false positive manually and at far lower cost, so this item is worth doing for automatic coverage, not as a prerequisite. Requires a new `LanguageBase` hook (`maintainer_url(name)` plus a parse method) because each registry exposes ownership differently: PyPI has no maintainer field in the JSON API and needs the `/pypi/<pkg>/json` `info.author`/`maintainer` fields or a scrape, npm has `maintainers[]` in the registry document, and Packagist has vendor namespacing that makes it nearly free. Cache per package alongside the popularity data. Treat a maintainer match as a strong reduction but not a veto, since an attacker could publish under a plausible-looking account name.

- [ ] Alert detail view — `pa alerts show <id>` (or `pa alerts` row expansion) showing the full risk signal breakdown: individual signal names, scores, and reasons (typosquat match, low popularity, install script, embedded binary, etc.) that contributed to the composite score. - [ ] Alert management — `pa alerts delete <id>` and `pa alerts clear` (with optional `--before <date>`, `--ecosystem`, `--risk-only` / `--advisory-only` filters) to remove stale or false-positive entries from the database. - [ ] Package allowlist — `pa allowlist add <package> [--ecosystem] [--version] [--reason]` to permanently suppress alerts for known-safe or in-house packages. Two distinct use cases: (1) internal packages hosted on a private registry that will always trigger low-popularity signals; (2) packages that have been manually reviewed and determined safe despite heuristic signals. Allowlist entries should be scoped (per-project or global), stored in config or the database, and visible in `pa allowlist list`. Allowlisted packages should be skipped by the daemon, pre-flight check, and post-install scan — not just suppressed at alert display time. Model the storage and CLI on the existing `cooldown_cleared` table and `pa cooldown allow` command, which already solve the same shape of problem (a user-granted, persisted, per-package exemption) — and subsume that command's surface, per "Subsuming `pa cooldown allow`" below.

  **Per-signal suppression.** A blanket allowlist is too coarse to be the only option: suppressing everything for a package also suppresses genuine OSV advisories and install-script signals that appear in a later version. Support `--signal <name>` (repeatable) to waive named signals only — `pa allowlist add somepkg2 --signal typosquat --reason "genuine v2 release line"` — leaving every other signal active. A bare `pa allowlist add` with no `--signal` remains the full-suppression form for genuinely trusted in-house packages. Waiving a signal should subtract it from the composite score rather than zeroing the report, so the remaining signals still gate normally; `pa allowlist list` must show which signals each entry waives, and `scan-project --details` should mark a suppressed signal as waived rather than hiding it, so a suppression can never silently outlive its justification.

  This is the practical answer to the false positive left by adoption-corroborated typosquat scoring (see the completed Phase 3 typosquat item): a genuine new major release such as `somepkg2` is gated until it accrues dependents, and `--signal typosquat` lets a maintainer or user clear exactly that one objection for exactly that one package without weakening anything else. It is a better fit for this case than shared-maintainer detection below, because it needs no per-registry ownership plumbing and expresses a decision the user has actually made. Consider `--expires <duration>` for the specific case of waiving a typosquat objection on a package expected to accrue adoption, so a temporary exemption does not become permanent by default.

  **Subsuming `pa cooldown allow`.** `pa cooldown allow <pkg> <ver>` already implements a user-granted, persisted, per-package exemption, so having two commands for "waive this objection" is one too many. Fold the *surface* into this feature — `pa allowlist add <pkg> --version <ver> --signal cooldown` — and have `pa allowlist list` show cooldown clearances alongside signal waivers, so users learn one command and can see every active exemption in one place. Keep `pa cooldown allow` as a documented alias rather than removing it: it appears in the README quick start and in agent workflows, and the pre-clearance path is load-bearing for unattended installs.

  Fold the surface, **not** the mechanism. Cooldown is not a risk signal and must not be modelled as one:

  - It contributes no score. Signals are `RiskSignal(name, score, reason)` summed into a composite, so a waiver subtracts a number; cooldown returns a `CooldownDecision` action directly, with nothing to subtract. `--signal cooldown` must route to `cooldown_cleared` (the existing storage, with its `cleared_at` semantics), not to score arithmetic.
  - It is version-specific and self-expiring — an objection to `foo==1.2.3` is moot after `period_days`, and clearances already expire on the same window. A typosquat objection attaches to a *name* and never expires on its own. So `--version` stays optional for signal waivers but is required for `--signal cooldown`, and `--expires` is meaningful for typosquat while cooldown keeps its existing implicit expiry.
  - The two must remain independently configurable. `pa run` deliberately evaluates the risk gate *before* the cooldown check, and the risk gate exists to catch things cooldown cannot (a typosquat on an old package). Collapsing them into one waiver would let clearing a cooldown prompt silently also clear a typosquat block, which is precisely the coupling the Phase 3 work removed.

- [ ] IDE/tool install policy — detect and surface package installations triggered by background processes (VS Code extensions, language servers, IDEs) using parent process chain; optionally block or require explicit approval for non-user-initiated installs
- [ ] Refactor sandbox target resolution — move hardcoded ecosystem logic in `_resolve_targets` and `_collect_new_packages` (runner.py) into `LanguageBase` hooks so language modules own their own scan targets and post-install package detection
- [ ] `pa config upgrade` command — append missing config keys (commented, with defaults) to the installed config file after an upgrade, so users are not silently missing new options; `--dry-run` prints a diff without writing
- [ ] Dynamic value-flag discovery — the static `_UV_PROJECT_VALUE_FLAGS`, `_UV_TOOL_VALUE_FLAGS`, `_PIPX_VALUE_FLAGS`, and `_PIP_VALUE_FLAGS` frozensets in `parsers/process_args.py` must be manually re-audited when tool versions change. Replace with runtime discovery: at parse time, use the resolved `argv[0]` path (already available in the parser) to invoke `<binary> <subcommand> --help`, parse the output to identify `--flag <VALUE>` forms, and cache the result keyed by resolved binary path + version string. This is necessary per-invocation rather than per daemon start because different projects can use different tool versions (e.g. a venv pip vs system pip). Fall back to the current static sets if the binary is unavailable, the help invocation fails, or the parse produces an empty result.
- [ ] `pylock.toml` `packages.marker` evaluation still ignores CLI cross-target/extras overrides and the target's platform — `_collect_pylock_packages` (`parsers/lockfiles.py`) now derives the target Python **version** for a *bare* invocation (no CLI target flag) by discovering, in uv's own precedence order, `VIRTUAL_ENV` (venv, `pyvenv.cfg`), then `CONDA_PREFIX` (conda/mamba environment, `conda-meta/python-*.json` — verified empirically that a real conda environment has no `pyvenv.cfg` at all, via a `micromamba`-created environment; the JSON record's own `"name"` field is checked to reject false-positive matches like a `python-dateutil` package), then a walked-up `.venv`, and seeds `dependency_groups` from the pylock's own top-level `default-groups` key — so a bare `uv pip sync pylock.toml`'s implicit version and group are both scanned correctly whether the target is a venv or an active conda environment, even when they differ from package-alert's own interpreter. Critically, once `VIRTUAL_ENV`/`CONDA_PREFIX` is set, its version lookup is terminal: an unreadable target does not fall through to a lower-priority `.venv`, since uv itself already committed to that environment. Three related gaps remain, all documented in `THREAT_MODEL.md`'s Out of Scope: (1) an explicit `--python-platform`, `--python-version`, or `--python <path>` CLI override is still parsed-and-discarded rather than overriding the discovered target — `uv pip sync --python-platform windows pylock.toml` run on Linux excludes Windows-marked packages from every gate even though uv installs them for the requested target; (2) the discovered target's **platform** (`sys_platform`/`platform_system`/`platform_machine`) is never derived from it, only its version — relevant only if the discovered environment was itself created for a different OS than package-alert runs on; (3) `--extra`/`--all-extras`/`--group` are similarly parsed-and-discarded, so a sync using them installs `extras`-gated packages (and dependency groups beyond `default-groups`) that still evaluate against the empty-set default and never get scanned. Fixing (1) requires parsing the CLI flag values and overriding the discovered-target environment dict (`marker_environment` in `_collect_pylock_packages`) rather than what the target's own metadata says. Fixing (2) requires a uv-platform-tag → marker-environment mapping (`windows`/`linux`/`macos`/`x86_64-manylinux2014`/`aarch64-apple-darwin`/etc. → `sys_platform`/`platform_system`/`platform_machine`), several of which (Android, iOS, wasm32-pyodide targets) don't correspond to real marker values at all and would need their own handling — plus, for the discovered-environment case, reading the target platform from its own metadata (`pyvenv.cfg`/conda-meta's `platform` field) rather than a CLI flag. Fixing (3) requires parsing repeated `--extra` occurrences and `--group`/`--all-extras` from the argv and threading the selected sets through `ParsedInstall` → `ProcessInstall` → `_Context` → `_resolve_query_packages`/`_preflight` down to `_collect_pylock_packages`'s `Marker.evaluate(environment=...)` call (merged with the `default-groups`/target-version seeds already in place).

## Phase 4 (Near-term evaluation)
- [ ] Install target snapshot memory usage — `FileSystemBackend` reads all files ≤ `snapshot_file_size_limit` into memory before each sandbox run. For large node_modules trees this may cause significant memory pressure or slowdowns. Gather real-world data on peak RSS during npm installs and evaluate whether streaming hashes, on-disk snapshots, or a lower default size limit are needed before recommending the filesystem backend for large ecosystems.
- [ ] Snapshot content compression — `FileSystemBackend` stores raw file bytes in a dict for restore purposes. Compressing each entry with `zlib` at snapshot time (and decompressing on restore) would reduce peak RSS significantly for node_modules trees, which are predominantly text (JS, JSON, TypeScript declarations) and typically compress 60–80%. This also enables raising `snapshot_file_size_limit` without proportional memory cost, improving restore coverage for large files that are currently excluded. Implement after gathering RSS baseline data from the item above.
- [ ] Unify `ParsedInstall` and `ProcessInstall` — the sandbox runner passes `ParsedInstall` (from `packagealert/parsers/process_args.py`, with `packages: list[str]`, `req_files`, `global_install`, `suggested_env`) to language hooks typed against `ProcessInstall` (from `packagealert/languages/base.py`, with `packages: list[PackageSpec]`). Currently bridged with `Any` annotations and docstrings. Unify into a single type so hook signatures are accurate and third-party plugins can rely on them.
