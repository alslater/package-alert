# Claude Instructions

- Use `uv` as the package management tool for this project. Prefer `uv sync`, `uv add`, `uv remove`, and other `uv` commands for dependency and environment management.
- Always run Python tooling from the project virtualenv. Prefer `.venv/bin/python`, `.venv/bin/pip`, and `.venv/bin/pytest`, or activate `.venv` before running Python-related commands.
- When running tests, prefer `.venv/bin/pytest` or `.venv/bin/python -m pytest`.
- Do not use the system `python`, `pip`, or `pytest` for this repository when the project virtualenv is available.
- After any Python file changes, run `.venv/bin/python -m ruff check .` and `.venv/bin/pyright` and fix all issues found before considering the task complete.
- Do not use any git write commands in this repository. Do not run commands such as `git add`, `git commit`, `git merge`, `git rebase`, `git cherry-pick`, `git tag`, `git push`, `git stash`, `git reset`, or any other command that mutates git state. The user will handle all git write operations.

## Auditing value-consuming flag lists

Several `frozenset` constants in `packagealert/parsers/process_args.py` list flags that consume the next argument (e.g. `_UV_PROJECT_VALUE_FLAGS`, `_UV_TOOL_VALUE_FLAGS`, `_PIPX_VALUE_FLAGS`, `_PIP_VALUE_FLAGS`). When these need auditing or updating, run the tool's own help output and compare:

```bash
# uv add / uv remove
uv add --help 2>&1 | grep -E "^\s+-"
uv remove --help 2>&1 | grep -E "^\s+-"

# uv tool install / upgrade
uv tool install --help 2>&1 | grep -E "^\s+-"
uv tool upgrade --help 2>&1 | grep -E "^\s+-"

# pipx
pipx install --help 2>&1 | grep -E "^\s+-"
pipx inject --help 2>&1 | grep -E "^\s+-"

# pip
pip install --help 2>&1 | grep -E "^\s+-"
```

For each flag line, include it in the frozenset only if it takes a value (shown as `--flag <VALUE>` or `-f VALUE`). Boolean flags (`--flag` with no `<VALUE>`) must be omitted. Update the `# Audited against: <tool> <version>` comment in the constant after each audit (`uv --version`, `pipx --version`, `pip --version`).

## Auditing the uv cache-layout assumptions

`PythonLanguage`'s cache-monitoring code hardcodes assumptions about uv's `~/.cache/uv` on-disk layout: `cache_paths()`, `poll_only_cache_paths()`, `cache_file_globs()`, `classify_cache_file()`, and the `_uv_wheel_index_entry_to_metadata()` / `_uv_sdist_index_entry_to_metadata()` / `_uv_index_name_dir()` / `_uv_git_wheel_leaf_to_metadata()` helpers and their `_UV_WHEEL_INDEX_TAGS_RE` / `_UV_WHEEL_INDEX_BUILD_HASH_RE` / `_UV_CACHE_HASH_RE` / `_UV_CACHE_SCHEMA_DIR_RE` regexes in `packagealert/languages/python.py`. uv does not document this layout as a stable public interface, and it has changed across cache-schema versions before (`wheels-v4` → `wheels-v6`, `sdists-v9`); a future uv release can rearrange it again without warning, silently breaking package detection (missed installs), causing duplicate/premature alerts, or reintroducing the inotify-watch-exhaustion problem this code exists to prevent — several rounds of exactly these bugs were found and fixed in the `fix-watch-overuse` branch by checking uv's actual behavior rather than assuming the existing code was still correct, including **two separate rounds** where an entire *kind* of install was missing coverage altogether, not just a shape variant of a kind already handled: a direct-URL wheel dependency (uv's `WheelCache::Url` bucket), and a wheel file committed directly to a Git repository (`WheelCache::Git` — note `WheelCacheKind::Git`'s own doc comment in uv's source claims "wheels can't be delivered through Git", but that comment is itself stale/wrong, contradicted by `distribution_database.rs`'s actual `BuiltDist::GitPath` handling — don't trust a doc comment over what the code actually does). Two misses of the same *category* (an install-source kind entirely absent, not a shape drift in one already handled) is a pattern, not a coincidence — treat step 3's `WheelCache` enum check as mandatory on every audit, not optional groundwork to skip when nothing else seems to have changed.

The inotify-watch-exhaustion problem this code exists to prevent has already reappeared once at a *different* level of the same tree: `sdists-v*`'s own index entries are as shallow as `wheels-v*`'s, but uv unpacks each source-build shard into a full extracted `src/` directory sitting right alongside the built wheel, and that `.whl` is an inotify-recursion sibling of `src/` — there is no depth-limited or path-excluding recursive watch available (watchdog/inotify's `recursive` is a flat boolean), so any watch deep enough to see the `.whl` is also deep enough to recurse into the whole unpacked source tree. `sdists-v*` is therefore in `poll_only_cache_paths()`, not `cache_paths()`: `CacheMonitor._poll_cache_dirs()` glob-scans it periodically (every `_MAINTENANCE_INTERVAL_SECONDS`) instead of holding a permanent recursive inotify watch on it. When auditing this code, don't assume every `cache_paths()`-shaped root is safe to watch recursively just because its own index entries are shallow — check whether anything *else* gets written under that same root first (a build's unpacked sources, extracted archive contents, etc.), the same way `archive-v0`/`git-v0` were excluded from `cache_paths()` entirely for containing the same kind of unbounded, zero-value directory growth.

Polling doesn't fully sidestep that same cost, either: `cache_file_globs()`'s `**/*.whl`-style patterns are recursive, so `_poll_cache_dirs()`'s glob walk still descends into every `src/` subtree under `sdists-v*` — `Path.glob()` has to enter a directory to learn it has no matches, so excluding a root from the inotify *watch* doesn't exclude it from the glob *walk*. Confirmed to take tens of milliseconds even for a modest cache and scale with its size. Because this happens on every maintenance interval forever, `CacheMonitor._poll_cache_dirs()` runs the actual glob/classify work (`_poll_cache_dirs_sync()`) via `asyncio.to_thread()`, not directly on the event loop, so it never blocks OSV lookups, DB writes, or other monitors' event processing for its duration. `_poll_cache_dirs_sync()` must stay a pure function of its inputs — no `asyncio.Queue.put_nowait()` or `self._poll_only_seen` mutation inside it, since those aren't thread-safe to call from a different OS thread than the event loop's — it returns `(current_snapshot, events)` instead: `current_snapshot` is each polled root's *complete* current set of classifiable `(path, identity)` pairs (not a delta), which the caller assigns wholesale over `self._poll_only_seen` (a full replacement, not a merge) so any root or artifact absent from this poll's result — deleted since the last one — is dropped simply by not being copied forward, with no separate "vanished" tracking needed. Also make sure `_run_maintenance_if_due()`'s next-deadline scheduling stays anchored to completion time, not the time the pass started: an expensive poll that itself takes longer than `_MAINTENANCE_INTERVAL_SECONDS` must still produce a deadline in the future, not one already expired the moment it's set (confirmed to otherwise cause continuous back-to-back maintenance passes with no rest between them). If you add a new poll-only-root scan, or add work to this one, keep the same split: any code path that runs on every maintenance tick and touches the filesystem (not just `sdists-v*`) should be considered for the same `asyncio.to_thread()` treatment before assuming a "just excluded from the watch" fix is sufficient on its own.

`classify_cache_file()`'s `.whl` branch deliberately classifies a source-build wheel as its own event even when its `sdists-v*/pypi/<name>/<version>` ancestor also independently classifies (an earlier ancestor-based suppression was removed after it was shown to silently drop a real install to zero events — see that branch's own comment and git history). This is safe from becoming a duplicate *alert*, not just a duplicate internal event, only because `daemon.py`'s dedup layer separately collapses the version-dir and `.whl` events for the same build, which land minutes apart in genuinely separate `_consume()` batches for a nontrivial build. That layer is two dicts, not one:
- `Daemon._processed_this_session`, keyed by the full `(ecosystem, package_name, version, project_path)` — this is what makes the version-dir and `.whl` events (same project_path, since both come from the cache monitor) collapse into one evaluation, while still keeping two *different* projects installing the same version as separate alerts (deliberately: collapsing on `project_path` would let one project's clean copy mask another's independently-compromised copy of the same name/version, the same risk `scoring.py`'s own scan path explicitly guards against).
- `Daemon._cache_only_completions`, keyed by the narrower `(ecosystem, package_name, version)` — no `project_path` — which additionally collapses two *separate* cache-monitor observations of the same version (e.g. a second, unrelated build) without ever suppressing a process-monitor event, since only a `source="cache"` completion is recorded there. This exists because `_resolve_package_dir()` returns no directories at all for a cache event (nothing has been extracted to disk yet), so a cache event's analysis is always weaker than a process event's — the full key alone would otherwise let a cache event that won a race permanently block the richer process observation of the very same install for the rest of the window.

Both dicts are bounded by `_DEDUP_WINDOW_SECONDS` (currently 300s, matching `_SITE_PACKAGES_WATCH_IDLE_SECONDS`'s own "how slow can a real install take" reasoning in `cache.py`) — not a permanent per-session membership set, since a cache event's `project_path=None` would otherwise make a genuinely later, separate reinstall of the same version indistinguishable from a duplicate for the daemon's entire uptime. A stale entry is also pruned proactively by `Daemon._dedup_pruning_loop()` (a background task started alongside `_update_check_loop()`/`_scheduler_loop()` in `Daemon._run()`), not just lazily when that exact key recurs — without it, a package version installed exactly once over the daemon's whole lifetime would leave its entry in memory forever.

If either the version-dir classification, `_processed_this_session`, `_cache_only_completions`, or `_dedup_pruning_loop()` is ever changed, re-verify the whole chain still prevents a real double-alert (two `store_alert()` rows and two notifications for one install) without reintroducing either of the two now-fixed regressions above — `store_alert()` itself has no uniqueness constraint to catch this at the DB layer.

**Re-run this audit whenever cutting a `prepare-X.Y.Z` release branch**, and any other time this project's `uv` dependency/toolchain version changes.

1. Check the installed uv version and compare against each affected constant/function's own `# Audited against: uv <version>` comment (add the comment if missing — treat its absence as "never audited," not as "no changes needed"):
   ```bash
   uv --version
   ```
2. Inspect a real, populated `~/.cache/uv` rather than reasoning from memory or documentation — this is what caught every layout bug found so far:
   ```bash
   find ~/.cache/uv/wheels-v* -maxdepth 4 | head -60
   find ~/.cache/uv/sdists-v* -maxdepth 5 | head -60
   ls -la ~/.cache/uv/wheels-v*/pypi/<some-package>/   # confirm symlink vs .http/.msgpack/.rev/.lock companions
   readlink ~/.cache/uv/wheels-v*/pypi/<some-package>/<leaf>   # confirm it still resolves into archive-v0
   ```
   Specifically re-verify: the cache-schema directory naming (`wheels-v<digits>`, `sdists-v<digits>` — confirm no new bucket name or version scheme), the index leaf shapes (`<version>-<tags>` and `<version>-<16-hex-build-hash>`), the companion-file suffixes alongside a leaf (currently `.http`, `.msgpack`, `.rev`, `.lock` — confirm no new suffix appeared), and the sdist-build wheel location under `sdists-v*` (currently `pypi/<name>/<version>/<revision-hash>/` or, when `uv`'s `BuildInfo::cache_shard()` is non-empty, one shard deeper — confirm the depth(s) are still exactly these).

   A real, populated cache only ever shows the *install-source kinds that machine has actually used*. `~/.cache/uv/wheels-v*` doesn't grow a `url/` bucket until someone runs `uv pip install <direct wheel URL>` on that machine, so its absence proves nothing — a bucket kind existing in uv's source but never yet observed on disk is exactly the gap that let the `url/` shape (see step 3) go unhandled for a full round of this audit. Don't stop at whatever bucket names happen to already exist; cross-check the full list uv itself defines (step 3's `WheelCache` enum) against what this code currently handles, and if a defined kind's on-disk shape hasn't been verified yet, generate it deliberately rather than skipping it:
   ```bash
   # Isolate from the real cache — never run uv commands against a real
   # ~/.cache/uv while testing an unfamiliar install pattern.
   mkdir -p /tmp/uv-audit-cache
   UV_CACHE_DIR=/tmp/uv-audit-cache uv pip install --python "$(which python3)" \
     --target /tmp/uv-audit-target "<direct wheel or sdist URL>"
   find /tmp/uv-audit-cache/wheels-v* /tmp/uv-audit-cache/sdists-v* -maxdepth 5
   rm -rf /tmp/uv-audit-cache /tmp/uv-audit-target
   ```
3. Cross-check against uv's actual source rather than trusting inference from directory names alone — the mechanism, not just the shape, has caused false assumptions before (e.g. a `<version>-<16-hex>` leaf name is not reliably a "build hash suffixed to the real version"; it's also uv's own `cache_key()` truncating an over-length version). Relevant files in `astral-sh/uv` (fetch via `gh api repos/astral-sh/uv/contents/<path>` or the GitHub UI, not by guessing):
   - `crates/uv-cache/src/wheel.rs` — `WheelCache`, the enum of every install-source bucket kind (`Index`, `Url`, `Path`, `Editable`, `Git`) and how each roots its own subtree. Check this FIRST: it's the authoritative list of shapes that exist at all. Don't trust this file's own doc comments over what the code in `distribution_database.rs`/`source/mod.rs` actually does — `WheelCacheKind::Git`'s doc comment says "wheels can't be delivered through Git", but `distribution_database.rs`'s `BuiltDist::GitPath` arm does exactly that (`wheels-v*/git/<url-digest>/<git-sha>/<wheel-filename-stem>`), and that mismatch was only found by a reviewer reading the actual persist code, not by trusting the comment or by a populated cache happening to contain one — cross-check every variant listed here against where it's actually constructed (next bullet), not just its doc comment.
   - `crates/uv-distribution-filename/src/wheel.rs` — `WheelFilename::cache_key()`
   - `crates/uv-distribution-types/src/build_info.rs` — `BuildInfo::cache_shard()`
   - `crates/uv-distribution/src/distribution_database.rs`, `crates/uv-distribution/src/source/mod.rs` — where wheels/sdists are actually persisted (`persist_extracted_wheel`, `.http`/`.rev`/`.lock` writing) and which `WheelCache` variant each install path actually uses. Grep this file for every `WheelCache::<Variant>` construction site and note which `CacheBucket` (`Wheels` or `SourceDistributions`) it's paired with and what gets passed as the leaf (a package name via `.wheel_dir(name)`, vs. the bare `.root()` with no name at all, vs. — `Git` specifically — `wheel.filename.stem()`, the whole wheel filename as the leaf). A variant's on-disk shape can differ between the wheel and sdist buckets even for the same variant (e.g. `Url`: `wheels-v*/url/<hash>/<name>/<leaf>` for a direct-URL wheel, but `sdists-v*/url/<hash>/<revision-hash>/...` — no name directory at all — for a direct-URL sdist), so verify each `(WheelCacheKind, CacheBucket)` pair separately rather than assuming symmetry.
   - `crates/uv-distribution/src/index/registry_wheel_index.rs`, `crates/uv-distribution/src/index/built_wheel_index.rs` — how uv itself re-reads its own cache
   - `crates/uv-cache/src/lib.rs` — `CacheBucket`, `Cache::persist_with_id` (the archive-v0 symlink)
4. If anything changed: update the affected regex/function, add or update its `# Audited against: uv <version>` comment, and add a regression test using the *exact* real directory shape observed in step 2 (not a simplified approximation) — see `tests/unit/languages/test_python.py`'s existing `test_classify_uv_*` tests for the established pattern.
