# Claude Instructions

- Use `uv` as the package management tool for this project. Prefer `uv sync`, `uv add`, `uv remove`, and other `uv` commands for dependency and environment management.
- Always run Python tooling from the project virtualenv. Prefer `.venv/bin/python`, `.venv/bin/pip`, and `.venv/bin/pytest`, or activate `.venv` before running Python-related commands.
- When running tests, prefer `.venv/bin/pytest` or `.venv/bin/python -m pytest`.
- Do not use the system `python`, `pip`, or `pytest` for this repository when the project virtualenv is available.
- After any Python file changes, run `.venv/bin/python -m ruff check .` and `.venv/bin/pyright` and fix all issues found before considering the task complete.
- Do not use any git write commands in this repository. Do not run commands such as `git add`, `git commit`, `git merge`, `git rebase`, `git cherry-pick`, `git tag`, `git push`, `git stash`, `git reset`, or any other command that mutates git state. The user will handle all git write operations.

## Auditing value-consuming flag lists

Several `frozenset` constants in `packagealert/parsers/process_args.py` list flags that consume the next argument (e.g. `_UV_PROJECT_VALUE_FLAGS`, `_UV_TOOL_VALUE_FLAGS`, `_PIPX_VALUE_FLAGS`, `_PIP_VALUE_FLAGS`). When these need auditing or updating, run the tool's own help output and compare:

```bash
# uv add / uv remove
uv add --help 2>&1 | grep -E "^\s+-"
uv remove --help 2>&1 | grep -E "^\s+-"

# uv tool install / upgrade
uv tool install --help 2>&1 | grep -E "^\s+-"
uv tool upgrade --help 2>&1 | grep -E "^\s+-"

# pipx
pipx install --help 2>&1 | grep -E "^\s+-"
pipx inject --help 2>&1 | grep -E "^\s+-"

# pip
pip install --help 2>&1 | grep -E "^\s+-"
```

For each flag line, include it in the frozenset only if it takes a value (shown as `--flag <VALUE>` or `-f VALUE`). Boolean flags (`--flag` with no `<VALUE>`) must be omitted. Update the `# Audited against: <tool> <version>` comment in the constant after each audit (`uv --version`, `pipx --version`, `pip --version`).

## Auditing the uv cache-layout assumptions

`PythonLanguage`'s cache-monitoring code hardcodes assumptions about uv's `~/.cache/uv` on-disk layout: `cache_paths()`, `poll_only_cache_paths()`, `cache_file_globs()`, `classify_cache_file()`, and the `_uv_wheel_index_entry_to_metadata()` / `_uv_sdist_index_entry_to_metadata()` / `_uv_index_name_dir()` / `_uv_git_wheel_leaf_to_metadata()` helpers and their `_UV_WHEEL_INDEX_TAGS_RE` / `_UV_WHEEL_INDEX_BUILD_HASH_RE` / `_UV_CACHE_HASH_RE` / `_UV_CACHE_SCHEMA_DIR_RE` regexes in `packagealert/languages/python.py`. uv does not document this layout as a stable public interface, and it has changed across cache-schema versions before (`wheels-v4` → `wheels-v6`, `sdists-v9`); a future uv release can rearrange it again without warning, silently breaking package detection (missed installs), causing duplicate/premature alerts, or reintroducing the inotify-watch-exhaustion problem this code exists to prevent — several rounds of exactly these bugs were found and fixed in the `fix-watch-overuse` branch by checking uv's actual behavior rather than assuming the existing code was still correct, including **two separate rounds** where an entire *kind* of install was missing coverage altogether, not just a shape variant of a kind already handled: a direct-URL wheel dependency (uv's `WheelCache::Url` bucket), and a wheel file committed directly to a Git repository (`WheelCache::Git` — note `WheelCacheKind::Git`'s own doc comment in uv's source claims "wheels can't be delivered through Git", but that comment is itself stale/wrong, contradicted by `distribution_database.rs`'s actual `BuiltDist::GitPath` handling — don't trust a doc comment over what the code actually does). Two misses of the same *category* (an install-source kind entirely absent, not a shape drift in one already handled) is a pattern, not a coincidence — treat step 3's `WheelCache` enum check as mandatory on every audit, not optional groundwork to skip when nothing else seems to have changed.

**Every shape-validating regex here is anchored with `\Z`, never `$`.** Python's `$` also matches immediately before a final newline, so a `$`-anchored pattern is not the exact validator these all claim to be — and Linux permits newlines in filenames (only `/` and NUL are banned), so it is reachable rather than theoretical. All five were affected (`_UV_CACHE_HASH_RE`, `_UV_CACHE_SCHEMA_DIR_RE`, `_UV_WHEEL_INDEX_BUILD_HASH_RE`, `_UV_WHEEL_INDEX_TAGS_RE`, `_DISTINFO_RE`): a directory literally named `deadbeefdeadbeef\n` passed the digest check and its whole subtree was then read as a real uv index path, classifying as a package that was never installed (confirmed empirically, and identical to a genuine digest). `_UV_CACHE_SCHEMA_DIR_RE` is the most consequential — it gates which roots get a RECURSIVE INOTIFY WATCH, and its own comment notes that admitting a lookalike "could reopen the inotify watch exhaustion this scoping was meant to prevent", so this is not purely a false-event concern. The fix anchors the PATTERNS rather than converting the ~19 `.match()` call sites to `.fullmatch()`, so a future call site cannot silently reintroduce it; if you add a regex to this family, use `\Z`. `packagealert/parsers/wheel.py`'s `_WHEEL_RE` (the shared PEP 427 filename parser) is a SIXTH member of this family and was fixed the same way. Its exposure differs from the five in `python.py`: the two `classify_cache_file()`/`inspect_package()` call sites are gated by `path.suffix == ".whl"`, which is exact and already rejects a trailing newline, and `_uv_git_wheel_leaf_to_metadata()` appends `".whl"` onto a stem, putting any newline mid-string where `_TAG_SET_RE`'s `[A-Za-z0-9_]+` rejects it — so no CURRENT caller could reach the bug, contrary to the review finding that reported it as a live false-install path. It is still anchored with `\Z`, because that protection is incidental to those callers rather than a property of the parser, and `parse_wheel_filename()` is shared, public, and reused by anything that later parses a name it did not itself construct. Verified against all 203 real wheel filenames on this machine: zero behaviour change on the genuine names, and the trailing-newline form now rejected for all 194 of them that are well-formed. Regression coverage: `test_parse_wheel_rejects_a_trailing_newline`. Regression coverage: `test_uv_shape_regexes_reject_a_trailing_newline` (parametrized over all five, asserting both that the newline form is rejected AND that the plain form still matches) and `test_classify_uv_index_entry_under_newline_digest_dir_is_rejected`.

`_uv_wheel_index_entry_to_metadata()`'s legacy `wheels-v4` "<name>-" prefix strip must try the PEP 503/427 FILENAME ESCAPE of the directory name — every run of `[-_.]` collapsed to a single `_` (`_PKG_NORM_RE.sub("_", ...)`) — not just the raw directory name and a naive `"-"`→`"_"` swap. A wheel filename embeds the distribution name in that escaped spelling, so a DOTTED name lives under `pypi/zope.interface/` with a leaf beginning `zope_interface-`. With only the two naive candidates neither matched, the UNSTRIPPED leaf was parsed, and `_UV_WHEEL_INDEX_TAGS_RE` matched it reading the NAME ITSELF as the version (`version="zope_interface"`, the real `6.0` absorbed as a build tag) — a junk OSV query and a bogus alert for a version that does not exist, for packages as common as `zope.interface`, `backports.zoneinfo`, `ruamel.yaml`. Confirmed empirically. The loop also now keeps trying the remaining candidates instead of `break`ing on the first that merely string-matches, so a candidate that matches but yields an unparseable leaf can't shadow a later one that would have worked. Regression coverage: `test_classify_uv_wheel_index_legacy_dotted_name_prefix`. Note a hyphenated leaf under an underscored directory (`pypi/my_pkg/my-pkg-1.0-...`) correctly stays unclassified — the escape never produces a hyphen, so that shape is not one uv emits.

The inotify-watch-exhaustion problem this code exists to prevent has already reappeared once at a *different* level of the same tree: `sdists-v*`'s own index entries are as shallow as `wheels-v*`'s, but uv unpacks each source-build shard into a full extracted `src/` directory sitting right alongside the built wheel, and that `.whl` is an inotify-recursion sibling of `src/` — there is no depth-limited or path-excluding recursive watch available (watchdog/inotify's `recursive` is a flat boolean), so any watch deep enough to see the `.whl` is also deep enough to recurse into the whole unpacked source tree. `sdists-v*` is therefore in `poll_only_cache_paths()`, not `cache_paths()`: `CacheMonitor._poll_cache_dirs()` glob-scans it periodically (every `_MAINTENANCE_INTERVAL_SECONDS`) instead of holding a permanent recursive inotify watch on it. When auditing this code, don't assume every `cache_paths()`-shaped root is safe to watch recursively just because its own index entries are shallow — check whether anything *else* gets written under that same root first (a build's unpacked sources, extracted archive contents, etc.), the same way `archive-v0`/`git-v0` were excluded from `cache_paths()` entirely for containing the same kind of unbounded, zero-value directory growth.

**An artifact BUNDLED inside an unpacked `src/` tree is file content, not an installed package.** Adding `sdists-v*` to `poll_only_cache_paths()` also feeds each source build's unpacked `src/` directory through `cache_file_globs()`' recursive artifact patterns (`**/*.whl`, `**/*.dist-info`, `**/*.tar.gz`), and `classify_cache_file()` matched on the artifact NAME before checking its uv path shape — so whatever an sdist happens to ship (test fixtures, vendored wheels, nested sdists) was reported as an install that never happened. Confirmed empirically: `sdists-v*/pypi/<name>/<version>/<revision>/src/fixtures/vendor-9.9-py3-none-any.whl` classified as `vendor 9.9`. `classify_cache_file()` now returns `None` for any path with `src` in `path.parts[:-1]`, placed before every branch so it covers all three artifact patterns rather than just `.whl`. This is safe because uv writes the BUILT wheel directly into the revision shard as a SIBLING of `src/`, never inside it — verified against a real populated cache, where the shard holds `metadata.msgpack`, the unpacked `<name>-<version>` directory, the `.whl` and `src/` side by side, and re-verified after the change that all 1681 real artifacts still classify. If a future uv layout ever moves a build OUTPUT under `src/`, this guard would hide it, so re-check the sibling relationship during the cache-layout audit rather than assuming it holds. That guard must be SCOPED to a validated `sdists-v<digits>` root, and only to a `src` component BELOW it — an unscoped `"src" in path.parts` check was tried first and is far worse than the bug it fixes. It also matched ordinary project layouts: a venv under `/project/src/.venv/lib/.../site-packages/` stopped classifying entirely, so installs in ANY project whose path merely CONTAINS a `src` component produced no events at all. Confirmed empirically — a silent miss across every such project, versus the single false event the guard exists to prevent. A `src` ABOVE the `sdists-v*` root is the user's own path, not uv's unpacked source tree, so it must not suppress anything. The check must also skip the `<name>/<version>` pair rather than testing bare membership: **`src` is a real PyPI package** (0.0.7), and its own entries put that component at the NAME position — `sdists-v*/pypi/src/<version>/<revision>/src-<version>-*.whl` — where a membership check suppressed both the built wheel AND the version directory, so installing it produced no event at all. uv's unpacked tree only ever appears as a child of the revision shard, which always follows `<name>/<version>`, so the scan starts after that pair. The name offset is bucket-dependent (`pypi/<name>` vs `index/<hash>/<name>` — the same shapes `_uv_sdist_index_entry_to_metadata()` validates), and depth BELOW the shard is deliberately not fixed: uv's optional build shard adds a level, and a real cache shows `src/` at three different depths. Two narrower rules were tried and are both wrong — requiring `src` to have a directory after it misses an artifact sitting DIRECTLY in `src/`, and a fixed depth breaks on the build-shard variant. Regression coverage pins both directions with three tests that fail under opposite mutations: `test_classify_uv_sdist_bundled_src_artifacts_are_not_installs` (bundled `.whl`/`.tar.gz`/`.dist-info` rejected, the real built wheel beside `src/` still classified) fails if the guard is removed, and `test_src_exclusion_is_scoped_to_uv_sdist_roots` (a venv under `src/`, and a `src` above the cache root) fails if it is unscoped. Verified after the change that all 1681 artifacts in a real populated cache still classify.

Polling doesn't fully sidestep that same cost, either: `cache_file_globs()`'s `**/*.whl`-style patterns are recursive, so `_poll_cache_dirs()`'s glob walk still descends into every `src/` subtree under `sdists-v*` — `Path.glob()` has to enter a directory to learn it has no matches, so excluding a root from the inotify *watch* doesn't exclude it from the glob *walk*. Confirmed to take tens of milliseconds even for a modest cache and scale with its size. Because this happens on every maintenance interval forever, `CacheMonitor._poll_cache_dirs()` runs the actual glob/classify work (`_poll_cache_dirs_sync()`) via `asyncio.to_thread()`, not directly on the event loop, so it never blocks OSV lookups, DB writes, or other monitors' event processing for its duration. `_poll_cache_dirs_sync()` must stay a pure function of its inputs — no `asyncio.Queue.put_nowait()` or `self._poll_only_seen` mutation inside it, since those aren't thread-safe to call from a different OS thread than the event loop's — it returns `(current_snapshot, events)` instead: `current_snapshot` is each polled root's *complete* current set of classifiable `(path, identity)` pairs (not a delta), which the caller assigns wholesale over `self._poll_only_seen` (a full replacement, not a merge) so any root or artifact absent from this poll's result — deleted since the last one — is dropped simply by not being copied forward, with no separate "vanished" tracking needed. Also make sure `_run_maintenance_if_due()`'s next-deadline scheduling stays anchored to completion time, not the time the pass started: an expensive poll that itself takes longer than `_MAINTENANCE_INTERVAL_SECONDS` must still produce a deadline in the future, not one already expired the moment it's set (confirmed to otherwise cause continuous back-to-back maintenance passes with no rest between them). If you add a new poll-only-root scan, or add work to this one, keep the same split: any code path that runs on every maintenance tick and touches the filesystem (not just `sdists-v*`) should be considered for the same `asyncio.to_thread()` treatment before assuming a "just excluded from the watch" fix is sufficient on its own. This isn't only a recurring-maintenance-tick concern, either: `start()`'s own `_seed_poll_only_baseline()` runs the identical recursive glob/classify walk once at startup (so `_poll_cache_dirs()`'s first real run only reports genuinely new artifacts, not a root's entire pre-existing contents), and got the same `asyncio.to_thread()` split for the same reason — `Daemon._run()` awaits `CacheMonitor.start()` directly, BEFORE installing signal handlers or creating consumer tasks, so a synchronous walk there would have blocked daemon startup itself (no SIGINT/SIGTERM handling, no event consumption at all) for the full scan, confirmed empirically. Check every call site that runs a poll-only root's glob walk, not just the recurring one, when auditing this.

`CacheMonitor._known_cache_roots` (a `dict[Path, _RootBaseline]`) exists to solve a narrower problem than it looks like: a root whose *initial* `_schedule_watch()` call fails (e.g. ENOSPC) is marked known immediately so a later successful registration retry doesn't treat it as brand-new and backfill-scan its entire pre-existing contents as a burst of stale alerts. An earlier version of this fix simply skipped the retry's backfill scan entirely for a known root (`backfill=False`) — that suppressed the stale-alert burst, but also meant a genuine install landing in the gap between the failed initial scheduling and the successful retry was neither observed live (no watch existed yet) nor ever backfilled afterward (backfill was unconditionally off), so it was silently and permanently lost — confirmed empirically. The fix instead snapshots each root's *currently matching* paths (`_snapshot_root_baseline()`) the moment it's first marked known, and every retry still runs a full backfill scan but passes that snapshot as `exclude` to `_backfill_scan()`, so only paths absent from the original snapshot — i.e. genuinely created during the gap — produce events; anything in the snapshot is treated as pre-existing and skipped before it ever reaches `classify_cache_file()` or `backfill_dedup.claim()` (deliberately: claiming it there would prevent a *later* real delete+recreate of that same stale path from ever being detected either). If you change `_reschedule_missing_watch()`, `_rescan_cache_paths()`, or `_backfill_scan()`'s `exclude` handling, re-verify both halves of this with a real reproduction: a pre-existing artifact from before the failed scheduling attempt must stay suppressed, and a new one created strictly after the known-root snapshot was taken (before the retry runs) must still produce exactly one event.

`start()`'s OWN initial watch registration has the identical gap one level earlier, and is fixed the identical way: it used to take the known-root baseline snapshot, then call `_schedule_watch()` directly with `will_backfill` left at its default (`False`) and never backfill-scan at all afterward — "normal startup deliberately never backfills a root's pre-existing contents" was true, but so was "normal startup never catches anything created strictly after the snapshot but before the watch goes live," which is a real, silent, permanent miss, not intentional behavior. Confirmed empirically (a fast concurrent install landing right at daemon startup produced zero events). `start()` now routes its initial registration through the SAME `_reschedule_missing_watch()` coordination the retry case uses — `will_backfill=True`, then a backfill scan excluding the very snapshot just taken — so the pre-existing-content suppression still holds (the snapshot is still the `exclude`) while anything created in the schedule gap is still caught. If you ever give `start()` a reason to diverge from `_reschedule_missing_watch()` again (e.g. a startup-specific fast path), re-verify this exact gap doesn't reopen — a pre-existing artifact must stay suppressed, and an artifact created between the baseline snapshot and the watch going live must still produce exactly one event, matching `_rescan_cache_paths()`'s own retry-case guarantee.

The fix above still had a narrower version of the exact same gap inside it, one level earlier still: `start()` took the known-root baseline snapshot itself — the call to `_snapshot_root_baseline()` that produces `exclude` — BEFORE `_reschedule_missing_watch()` was even invoked, i.e. before `_schedule_watch()` had scheduled anything at all. A file created WHILE that snapshot's own `glob()` call was still executing (a real possibility — the whole reason it runs via `asyncio.to_thread()` is that it can take real time for a large tree) is matched by that very `glob()` call and gets recorded straight into `exclude` as "pre-existing," with no watch alive yet to observe its creation live either — neither a live `on_created()` (no watch existed for that whole gap) nor the backfill scan moments later (its own identity now matches the snapshot's `exclude` set, so `_backfill_scan()` skips it before it ever reaches `classify_cache_file()` or `backfill_dedup.claim()` — see `_backfill_scan()`'s own docstring on `exclude` being checked before either). A real install with zero events, not merely a delay — confirmed empirically, and distinct from the "artifact created between snapshot and watch-going-live" gap the paragraph above already fixed: that one is closed by `will_backfill=True`'s live watch catching anything AFTER the snapshot completes; this one is a file the snapshot's own glob() call itself already absorbed, DURING its own execution, before scheduling even starts.

The fix adds a `snapshot_exclude_after_schedule: bool` parameter to `_reschedule_missing_watch()`, set `True` only by `start()`'s own two call sites (cache-paths roots and site_packages_dirs) — never by `_rescan_cache_paths()`'s retry path, which never re-takes this snapshot at all; it only ever REUSES the one `start()` already recorded via `_known_root_exclude()`, so it never had this narrower gap to begin with. When set, the caller passes `exclude=None` and does NOT take any snapshot of its own beforehand; `_reschedule_missing_watch()` takes it itself, at one of two different points depending on whether `_schedule_watch()` succeeds — NOT unconditionally right after `watches[path] = tracked`, which was tried first and reopened a different, separate invariant: a root that EXISTS at this call but whose `_schedule_watch()` itself FAILS (e.g. ENOSPC) still needs a stale baseline recorded for it (see `self._known_cache_roots`'s own docstring and `test_rescan_does_not_backfill_root_that_existed_but_failed_initial_scheduling`), so a LATER successful registration retry excludes this stale content rather than backfilling it as a burst of alerts purely because scheduling was delayed — confirmed empirically that snapshotting only in the success path silently reopened that exact bug (4 existing tests failed). The corrected version snapshots in the FAILURE path too (right there, before returning `False`) when `path.exists()` — there's no watch to race against there, since nothing was ever scheduled, so no live-vs-snapshot gap exists to close in that branch — and only defers the snapshot until after `watches[path] = tracked` in the SUCCESS path, where the watch's `backfill_dedup` is already open (see `_schedule_watch()`'s `will_backfill` docstring) and a file created during THIS walk is instead caught live by the watch, arbitrated by `_BackfillDedup`'s existing scan-vs-live-watch coordination exactly like any other file created during the backfill scan itself — no new mechanism needed, just the already-existing one now actually covering this window instead of being bypassed by it. If you touch `_reschedule_missing_watch()`'s snapshot timing again, re-verify BOTH invariants with a reproduction: a file matched by the snapshot's own `glob()` call (success path) must still be reported, not absorbed as pre-existing; and a root that exists but fails to schedule must still have SOME baseline recorded for a later retry to exclude against.

`_seed_poll_only_baseline()` has a THIRD variant of this exact same class of gap, and it's the one variant that can't be closed by "run a backfill scan afterward" at all: a poll-only root (uv's `sdists-v*`) is NEVER watched, by design (see `poll_only_cache_paths()`'s own docstring on why a permanent recursive watch there is unsafe) — there is no live signal whatsoever to catch an artifact created WHILE `_seed_poll_only_baseline_sync()`'s own recursive glob/classify walk is still running, the way `will_backfill=True` catches the analogous gap for a watched root. A real sdist build landing in the tree at the exact moment this walk's `glob()` happens to pass through its directory used to be swallowed straight into the baseline as pre-existing — permanently missed, since every later `_poll_cache_dirs()` call only ever reports what's NOT already in the baseline. Confirmed empirically (0 events for an artifact created during the seed walk). The fix is a startup cutoff, not a backfill: `_seed_poll_only_baseline()` captures `time.time()` immediately before the walk starts (minus `_SEED_BASELINE_CUTOFF_SAFETY_MARGIN_SECONDS`, currently 0.5s — see that constant's own docstring for why an EXACT, unpadded comparison isn't safe: `time.time()` and a freshly-`stat()`'d `st_mtime` are not guaranteed to agree at sub-second precision even for genuinely sequential operations, confirmed as a real, repeatable clock-source skew on this platform, not a scheduling fluke), and `_seed_poll_only_baseline_sync()` excludes any entry whose `st_mtime` is not strictly before that (margin-adjusted) cutoff from the returned baseline — such an entry is then simply absent from what gets recorded, so the very next real `_poll_cache_dirs()` call correctly treats it as new. A test fixture representing "genuinely pre-existing" content must backdate its mtime (see the `_backdate()` test helper) rather than relying on being created with zero delay before `start()` — that delay alone is not reliably larger than the safety margin, and isn't the property this fix is supposed to depend on anyway.

`_RootBaseline` — the snapshot type `_known_cache_roots` stores — records `_entry_identity()` (lstat, not stat) for both the root itself and every snapshotted entry, not just their pathnames. A pathname-only exclude set was tried first and confirmed broken: a path present in the snapshot can be deleted and recreated at the exact same name while the watch is still unavailable (a same-version reinstall, `uv cache clean` followed by a rebuild landing on the same cache key), and no live watch exists for that whole gap to observe the replacement either, so excluding by pathname alone silently and permanently lost that genuine reinstall — indistinguishable, from the exclude set's point of view, from the stale content it was meant to suppress. `_backfill_scan()`'s `exclude` handling now only skips an entry if it's present in the baseline AND its CURRENT identity still matches the one recorded at snapshot time; a changed or now-unresolvable identity falls through to normal classification. One level up, `_rescan_cache_paths()`'s `_known_root_exclude()` helper checks the ROOT's own identity before reusing a stored baseline at all — if the root itself was deleted and recreated (not just one entry under it) while unwatched, every path inside is unconditionally new content regardless of pathname matches, so a changed root identity invalidates the whole baseline: it's simply dropped from `self._known_cache_roots` (see that dict's own paragraph below for why NOT replaced with a fresh one) and nothing is excluded for that pass, exactly like a genuinely new root. If you touch this mechanism again, verify all three cases empirically: an untouched stale entry stays suppressed, a same-path delete+recreate during the gap produces its own event, and a whole-root delete+recreate during the gap backfills everything inside the new root.

**A baseline snapshot taken while NO watch is live must be bounded by the startup cutoff; one taken after the watch is live must not be.** `_snapshot_root_baseline()` takes an optional `cutoff` for exactly this. `_reschedule_missing_watch()`'s two FAILURE paths (the `except` around `_schedule_watch()`, and `tracked is None`) record a baseline so a later successful retry excludes stale content rather than replaying it — but precisely BECAUSE scheduling failed, nothing is observing the root while that recursive glob walk runs, and whatever it records becomes the retry's permanent `exclude`. An artifact created during the walk was recorded as stale and then skipped by the retry's own backfill: reported on no scan, ever. Confirmed empirically. An earlier comment at that site actively asserted the opposite ("There is no watch here to race against... has no live-vs-snapshot gap to close") — the absence of a watch is what makes it dangerous, not what makes it safe. Both failure paths now pass `self._poll_only_startup_cutoff`. The SUCCESS path is ALSO bounded, and an earlier version that left it unbounded was itself a confirmed permanent miss. The justification used then — "the watch is live during the snapshot" — is true but answers the wrong question: the live watch covers only from the moment `_schedule_watch()` made it live, not the window between the daemon's startup cutoff and that moment, during which nothing observes the root. An artifact created in that window was seen by nothing live, swept up by the unbounded snapshot as stale, and excluded by `_backfill_scan()` — reported on no scan, ever (`test_start_reports_artifact_created_before_the_watch_went_live`). `_backfill_new_contributors()`'s and the post-backfill `known_content` refreshes DO stay unbounded, and that is correct: both act only on roots ALREADY in `watches`, so the watch has been live continuously since registration and there is no uncovered window — the distinction is "has this root ever been unwatched since the daemon started", not "is a watch live right now". Regression coverage: `test_failed_schedule_baseline_does_not_swallow_artifact_created_during_it`. Any fixture representing "pre-existing" content for a failure-path test must be backdated via `_backdate()`, since a bare `touch()` now correctly reads as created after the daemon started — three existing tests needed this when the bound was added.

**A baseline used as `_backfill_scan()`'s `exclude` may only record paths that actually CLASSIFY, never bare glob matches.** `_snapshot_root_baseline()` originally recorded every match, with no classification — and that snapshot becomes `_TrackedWatch.known_content`, which `_backfill_new_contributors()` passes as `exclude`, whose check runs BEFORE classification. A root's merged `globs` is the UNION across every contributing plugin (see `_discover_cache_dirs()`), so one plugin's BROAD pattern (e.g. `**/*`) can match a path only a DIFFERENT plugin can classify. Recording that match marked it "already accounted for" when nothing had ever accounted for it: once the other plugin appeared as a new contributor, its catch-up backfill skipped the path at the exclude check and it was never reported, on that rescan or any later one — a permanent silent miss. Confirmed empirically. The fix mirrors `_seed_poll_only_baseline_sync()`'s own long-standing `if _classify_cache_path(entry):` gate, and also covers the transient case (a partially-written leaf that isn't classifiable YET must stay reportable once it becomes so). Regression coverage: `test_snapshot_baseline_does_not_exclude_unclassifiable_glob_match`. Note this adds a classify call inside the snapshot walk, which shifts classify-call accounting for any test that counts them — `test_backfill_scan_does_not_claim_transiently_unclassifiable_path` asserts 3 (backfill attempt, live retry, post-backfill snapshot) rather than 2; its own core assertion (exactly one event from the live retry) is unchanged. `_classify_cache_path()` is safe to call here even though this runs under `asyncio.to_thread()`: it only reads and never touches `self._queue` or any asyncio-owned state, which is why `_poll_cache_dirs_sync()` already calls it off-thread too.

**A LEAF artifact's identity and a ROOT directory's identity are deliberately different widths, and swapping them breaks in opposite directions.** `_entry_identity()` (leaves) returns `(st_dev, st_ino, st_ctime_ns)`; `_root_identity()` (cache roots) returns only `(st_dev, st_ino)`. The ctime component exists because `(st_dev, st_ino)` alone is not a complete artifact identity — a filesystem can hand the same inode straight back out after a delete, and ext4 reuses inodes readily. That matters most on a POLL-ONLY root, which by design has no watch and therefore no delete event to disambiguate with: `_poll_cache_dirs_sync()`'s `still_present` carries an entry forward whenever its identity is unchanged, so an inode-reusing delete+recreate would keep the STALE entry and skip the replacement on that poll and every later one — a permanent silent miss. ctime is the right third component rather than mtime because it is set on inode creation and cannot be back-dated from userspace (`os.utime()` moves mtime but leaves ctime current), and because for a non-directory it only ever ADDS discrimination, so two genuinely distinct artifacts can never be collapsed by it. It is applied to non-directories ONLY: a directory's ctime changes whenever an entry is added or removed directly beneath it, and uv's `sdists-v*/pypi/<name>/<version>` version dir — which itself classifies — gains a revision shard, then a `src/` tree, then the built wheel as ONE build progresses. Including ctime there made each step look like a new `(path, identity)` and re-reported the same install on poll after poll, each a separate `store_alert()` row and notification — confirmed empirically (three events for one build). Symlinks are deliberately NOT excluded: `lstat()` reports a symlink-to-directory as a link, so uv's index leaves keep the component the delete+recreate case needs. `_identity_from_stat()` exists so the scanners that build an identity from an lstat they already hold stay in step with `_entry_identity()` rather than drifting from its directory special-case. Regression coverage: `test_version_dir_not_re_reported_as_its_build_progresses`. Note the local filesystems here (ZFS, tmpfs) were measured NOT to reuse inodes across several allocation patterns, so a test that merely deletes and recreates passes even without the fix on this host. A dedicated test for the reuse case was attempted and then REMOVED as unreliable: three successive versions each passed under a regressed `_entry_identity()` for a different reason — comparing tuples it built itself (tautological), deriving the "stale" baseline from the function under test (differs under any implementation), and patching `_entry_identity` for the poll (so the regressed version never ran). Do not re-add one casually; if you try, mutation-test it against BOTH a bare 2-tuple and a constant third component before trusting it. The property is not unprotected: 22 existing tests fail under either mutation.

Applying that same widened identity to a cache ROOT was tried and is wrong: a directory's ctime changes every time a child is created or removed inside it, which for a cache root is the constant, normal case. `_known_root_exclude()` then concluded the root had been deleted and recreated on the very first install after the baseline was taken, discarded the whole exclude baseline, and the next backfill replayed that root's genuinely pre-existing content as brand-new alerts — caught by `test_rescan_backfills_artifact_created_during_failed_watch_gap`. A root's own inode is stable across changes to its contents, which is exactly the question `_known_root_exclude()` asks ("same directory, or one recreated at this path?"), and a root has the explicit watchdog delete event (`_still_watching()`) as a stronger signal that leaves on a poll-only root have no equivalent of. If you change either helper, keep them separate — `_EntryIdentity` is aliased so the leaf width is defined once and threaded opaquely through `_RootBaseline.entries`, `_BackfillDedup`, `self._poll_only_seen` and every snapshot/compare site.

`_known_root_exclude()` used to snapshot-and-STORE a fresh `_RootBaseline` into `self._known_cache_roots` whenever it had none to reuse — both for a root genuinely new to this rescan (never in the dict at all) and for a root whose identity had just changed (the rebuild case in the paragraph above) — and returned `None` (unfiltered) for THAT call either way. This was itself a bug: only `start()` ever has a legitimate "this content predates the daemon's own monitoring" claim to make (see `self._known_cache_roots`'s own docstring on why normal startup deliberately never backfills a root that already existed when it ran) — a root `_rescan_cache_paths()` discovers for the FIRST TIME, or whose identity just changed, has nothing that predates the daemon's own attempt to watch it. If THAT root's very first `_schedule_watch()` call then fails (e.g. ENOSPC), `_reschedule_missing_watch()` returns before `_backfill_scan()` ever runs — nothing was ever scanned or reported for it — but the snapshot `_known_root_exclude()` already stored was still there, and the NEXT rescan's retry reused it as `exclude` once scheduling finally succeeded, excluding content that had NEVER actually been backfilled. Confirmed empirically: a malicious install already present the instant a brand-new cache root was created (e.g. a uv cache-schema upgrade immediately followed by an install) produced zero events across a failed-then-successful schedule retry. The fix: `_known_root_exclude()` no longer snapshots or stores anything in either of those two cases — it simply returns `None` and leaves `self._known_cache_roots` without an entry for that root, so EVERY subsequent call for it (on each rescan retry) takes the same "nothing known yet" branch and stays fully unfiltered, until scheduling finally succeeds and `_rescan_cache_paths()`'s own `if d in watches: continue` guard means this method is never called for that root again. If you touch `_known_root_exclude()` again, verify with a reproduction where the FIRST `_schedule_watch()` attempt for a brand-new (or just-rebuilt) root fails and a LATER retry succeeds — content present at the root's very first appearance must still be reported on that successful retry, not silently excluded by a baseline nothing ever actually backfilled against.

`_snapshot_root_baseline()` — the glob walk that builds a `_RootBaseline` for `_known_cache_roots` above — is called from both `start()` and `_rescan_cache_paths()` (via `_known_root_exclude()`) using `asyncio.to_thread()`, the same split already established for `_poll_cache_dirs_sync()`/`_seed_poll_only_baseline_sync()` (see the polling paragraph above). It was initially added as a direct, synchronous call in both places — a populated cache root would then block the whole event loop for the full glob-walk duration, and since `Daemon._run()` awaits `CacheMonitor.start()` before installing signal handlers or creating consumer tasks, that meant no SIGINT/SIGTERM handling and no event consumption for that whole duration at daemon startup — confirmed empirically (0 event-loop ticks during a slowed-down synchronous walk). Unlike `_backfill_scan()`'s own synchronous call inside `_reschedule_missing_watch()` (which deliberately runs on the event loop, right after `_schedule_watch()`, to close a narrow race window against `_BackfillDedup` — see that method's docstring), `_snapshot_root_baseline()` has no such ordering constraint: it only reads the filesystem and writes to `self._known_cache_roots`, a plain dict never touched concurrently since `_rescan_cache_paths()` is only ever called sequentially from `events()`'s own loop. If you add another call site for this snapshot, or replace it with different traversal logic, give it the same `asyncio.to_thread()` treatment rather than assuming a "just a dict lookup" glob walk is cheap enough to skip it — the poll-only baseline mistake above was made for the same reason.

`_snapshot_root_baseline()` had its own version of the exact class of bug `_poll_cache_dirs_sync()`'s `incomplete_roots` and `_seed_poll_only_baseline_sync()`'s `incomplete_roots` already exist to prevent, just on the WATCHED-root side rather than the polled-root side: if a glob PATTERN raised partway through this snapshot's own walk (a transient I/O error on part of a large tree, not a malformed-pattern failure — the pattern list itself is fine, one instance of iterating it hit a transient error), the returned `_RootBaseline.entries` was silently treated as a COMPLETE accounting of the root's pre-existing contents regardless — with no signal to any caller that it might be missing entries. Since this baseline is used as `_backfill_scan()`'s `exclude` set (see `_RootBaseline`'s own paragraph above), an entry the failed pattern missed simply isn't in `exclude.entries`, so the REAL backfill scan that runs moments later — its own, separate `glob()` call, which can easily succeed even though the snapshot's identical-looking call just failed, since the two are two independent, momentary filesystem operations — does not exclude it, classifies it, and reports it as a brand-new install, even though it's genuinely stale content that predates the daemon. Confirmed empirically: a pre-existing wheel, missed only by the snapshot's own failed glob pattern, fired as a spurious "new install" event during `start()`'s own backfill scan.

Unlike the polled-root `incomplete_roots` mechanisms, which merge an incomplete pass with the PRIOR baseline (there's always a prior poll's state to fall back on), `_snapshot_root_baseline()` has no prior state to merge with — it's the very first snapshot ever taken for this root. Two things had to change: first, `_RootBaseline` gained an `incomplete: bool` field (`False` by default), set `True` if any glob pattern still fails after retries; `_backfill_scan()` now treats an incomplete `exclude` as `exclude=None` for that whole scan — excluding nothing, rather than trusting a known-partial baseline — matching this module's standing "an occasional duplicate/stale alert over silently trusting inaccurate data" philosophy rather than attempting a per-entry reconciliation against a set already known to be unreliable. Second, and more importantly, since this snapshot runs ONCE per root at registration time (not on a recurring poll the way `_poll_cache_dirs_sync()`'s equivalent does), it's worth PREVENTING the incomplete case in the common transient-blip scenario rather than just falling back gracefully from it: a raising glob pattern is retried up to `_ROOT_BASELINE_GLOB_RETRIES` times (a short `_ROOT_BASELINE_GLOB_RETRY_DELAY_SECONDS` delay between attempts — see that constant's own docstring for why a short fixed retry, not `OsvClient.batch_query()`'s exponential backoff tuned for a remote API, is the right shape for a local filesystem glob) before giving up on that pattern and marking the baseline incomplete. If you touch `_snapshot_root_baseline()`, `_RootBaseline`, or `_backfill_scan()`'s `exclude` handling again, verify both directions empirically: a transient glob failure that the retry rescues must still correctly suppress the pre-existing content it would have missed, and a glob failure that exhausts every retry must still report that content once (the accepted fallback cost) rather than either silently suppressing it forever or crashing.

**A root returned by BOTH `cache_paths()` and `poll_only_cache_paths()` is incoherent, not a supported configuration — and the watched side loses.** The two are independent duck-typed hooks with no cross-validation, so nothing stops a plugin returning the same `Path` from each, but `poll_only_cache_paths()`'s own contract says such roots are "scanned periodically INSTEAD OF watched with a recursive inotify watch", precisely because a recursive watch there "would risk exhausting the inotify watch budget". Honouring both gave such a root a recursive watch AS WELL AS the periodic walk — confirmed empirically: a shared root holding 251 subdirectories was scheduled with `is_recursive=True`, reintroducing the exact exhaustion this whole branch exists to fix, and the same install was emitted TWICE (once live, once from the poll). `_watched_paths()` (the accessor `_discover_cache_dirs()` passes to `_discover_dirs_by()`) drops the overlap and logs a warning naming the plugin. Poll-only wins because it is the strictly safer side: a polled root is still fully covered, just with more latency, whereas dropping the poll instead would leave a root that must not be watched with no coverage at all. Resolve this PER PLUGIN inside that accessor, not by diffing the two discovery results afterwards — an earlier version ran a second full `_discover_dirs_by()` pass purely to ask the question, which re-invoked every plugin's hooks an extra time and broke `test_cache_monitor_start_skips_buggy_cache_paths_plugin`'s call-count assertion. `_poll_only_paths()` is module-level for the same reason: two call sites need the identical accessor, and two copies would be two chances to drift. Regression coverage: `test_root_returned_by_both_hooks_is_polled_not_watched` (asserts BOTH that no watch is scheduled AND that the poll still reports the install).

The overlap check must compare on a NORMALISED basis, not by raw `in`. `poll_only_cache_paths()` is duck-typed, so a plugin can return `list[str]` instead of `list[Path]` — and a `str` never compares equal to a `Path`, so `[p for p in watched if p in poll_only]` silently found no overlap and left the root in the RECURSIVELY WATCHED set. Meanwhile `_discover_dirs_by()`'s own validation rejected that identical return and dropped the root from polling altogether: a root the plugin had explicitly declared poll-only ended up recursively watched (40 subdirectories in the reproduction) and polled by nothing at all — precisely the inotify exhaustion this whole mechanism exists to prevent, reached through a contract violation rather than a raise. Confirmed empirically. Note the "keep the watch when the hook is unusable" fallback from the paragraph below does NOT help here and actively hurts: since poll discovery rejects the same malformed return, keeping the watch buys no coverage, only the watch. A malformed ELEMENT is therefore still honoured as a declaration — a `str` spelling of the same directory is the plugin saying "this root is poll-only", and suppressing the watch costs it nothing it would otherwise have had, while the exclusion-reconciliation still guarantees the poll (with real globs). Non-path-like elements are skipped rather than raising, so one bad element cannot discard well-formed ones beside it; a genuinely non-list return still raises and falls through to the keep-the-watch path, which remains correct for a plugin that declared no overlap at all. Verify all four cases: well-formed overlap (not watched, polled), malformed overlap (not watched, polled), no overlap declared (watched, not polled), hook raises (watched, not polled). Regression coverage: `test_malformed_poll_only_declaration_still_suppresses_the_watch`.

That exclusion must never be able to leave a root with NO coverage, and as first written it could. `_watched_paths()` decides the exclusion from its OWN `poll_only_cache_paths()` call, but `_discover_poll_only_cache_dirs()` calls that duck-typed hook AGAIN, independently — so a plugin that succeeds on the first call and raises (or stops reporting the root) on the second had the root dropped from watching AND absent from polling: monitored by nothing at all. Confirmed empirically. Calling the hook twice inside `_watched_paths()` and intersecting the readings was tried and does NOT close it — the poll-side call is a THIRD invocation that can fail on its own, and a reproduction with a hook failing only on that call still produced zero coverage. Re-deriving the exclusions in `_discover_cache_dirs()` was also tried and is wrong for a different reason: it re-invokes every plugin's hooks, which broke `test_cache_monitor_start_skips_buggy_cache_paths_plugin`'s call-count assertion and three reseed tests. The fix records each excluded root — WITH the excluding plugin's own `cache_file_globs()` — into `self._poll_only_exclusions` at the moment `_watched_paths()` drops it, and `_discover_poll_only_cache_dirs()` unions back in any of those roots its own pass failed to report. The globs must be captured at exclusion time: reconciliation has no other source for them when poll-only discovery returns nothing at all, and a root polled with an empty glob list is covered in name only — confirmed, since deriving them from the other discovered roots yielded `[]` and the test still saw zero events. State is per-`CacheMonitor`, never module-level: a module-level set leaked across tests and broke six of them. Regression coverage: `test_overlap_root_stays_covered_when_poll_only_hook_later_fails`. Note its artifact must be created strictly after `_SEED_BASELINE_CUTOFF_SAFETY_MARGIN_SECONDS` has elapsed past `start()`, or the startup cutoff correctly withholds it and the test fails for an unrelated reason.

`_discover_dirs_by()` (the shared implementation behind `_discover_cache_dirs()` and `_discover_poll_only_cache_dirs()`) silently omits a language plugin's roots entirely from its return whenever that plugin's `cache_file_globs()`/`cache_paths()`/`poll_only_cache_paths()` raises — by design, so one buggy plugin can't stop every other plugin's roots from being discovered. That's fine for `_discover_cache_dirs()`'s only consumers (`start()`, `_rescan_cache_paths()`), since `self._known_cache_roots` is never wholesale-replaced from that result (see its own paragraph above) — a root missing this call, for any reason, just means "nothing to add or retry this pass." It is NOT fine for `_poll_cache_dirs()`, which wholesale-replaces `self._poll_only_seen` from `_discover_poll_only_cache_dirs()`'s result every poll: a root's OWN plugin failing transiently on one poll made that root indistinguishable from "genuinely deleted," wiping its baseline outright, and once the plugin recovered, every pre-existing artifact under that root replayed as a brand-new event — confirmed empirically, and especially bad once `daemon.py`'s `_DEDUP_WINDOW_SECONDS` has elapsed, since nothing there catches the replay as a duplicate either. `_discover_dirs_by()` therefore returns `(dirs, failed)` — `failed` is `True` if ANY plugin's hook raised this call — and `_poll_cache_dirs()` only wholesale-replaces `self._poll_only_seen` when `failed` is `False`; on a failed pass it instead merges the new snapshot ON TOP of the existing state, so a root only gets pruned once a SUCCESSFUL discovery pass positively confirms it's gone. `_discover_cache_dirs()` deliberately ignores the `failed`/`succeeded_plugins` half of this return (it never wholesale-replaces, so there's nothing for it to lose) — don't "fix" it to consult those two too, and don't let a future wholesale-replacement consumer of either discovery method skip checking `failed` the way this one originally did. `_seed_poll_only_baseline()` does NOT get the same pass — see its own paragraph below for why ignoring `failed` there was itself a bug, not a safe simplification. `_discover_cache_dirs()` does now also return `owning_plugins` (it used to discard all three) — see the `_backfill_new_contributors()` paragraph further below for why that one specifically, unlike `failed`/`succeeded_plugins`, is needed even by a non-wholesale-replacement consumer.

`_discover_dirs_by()`'s per-plugin `try/except` catches a RAISED exception from `cache_file_globs()`/`get_paths(lang)` (`cache_paths()`/`poll_only_cache_paths()`), but originally did nothing to validate what those calls RETURNED when they didn't raise — both are duck-typed, third-party-implementable hooks (see `LanguageBase`), and nothing stops a plugin from returning `None`, a non-iterable, or a list containing the wrong element type instead of raising. This mattered in two genuinely different ways, both confirmed empirically. First: `for p in paths:` runs AFTER the `try` block ends, so a plugin returning `None` for `paths` raised an unhandled `TypeError` right there, escaping `_discover_dirs_by()`'s own per-plugin isolation entirely and preventing every OTHER, well-behaved plugin's roots from being discovered on that call too — not just the misbehaving plugin's own root. Second, more subtly: a plugin returning a list containing a non-`Path` element (e.g. a bare `str`) does NOT raise anywhere inside `_discover_dirs_by()` itself — `p not in globs_by_path`/`.setdefault()` both work fine on a `str` key — so it silently passed straight through into the returned path list, and only blew up later, in a caller with no isolation of its own around it at all: `start()`/`_rescan_cache_paths()` both call `d.exists()` unconditionally on every discovered "path," and a `str` has no such method — an unhandled `AttributeError` there, confirmed to kill daemon startup or crash the whole cache-monitor consumer task out of `events()`'s loop, well outside any per-plugin boundary. Both `globs` and `paths` are now validated INSIDE the guarded `try` block — `isinstance(globs, list) and all(isinstance(g, str) for g in globs)`, `isinstance(paths, list) and all(isinstance(p, Path) for p in paths)` — and a failure either check raises `TypeError` from inside the same `try`, so a malformed return is treated exactly like a raised exception: caught by the existing `except Exception:`, logged, and isolated to that one plugin via the ordinary `failed=True; continue` path, with every other plugin's roots still reported normally. An empty list for either (a plugin genuinely has nothing to report yet) is NOT treated as malformed — only a genuinely wrong TYPE is rejected; `succeeded_plugins.add()` below already handles the "succeeded but reported nothing" case correctly. If you add a third duck-typed hook to this dispatch loop, or change what `get_paths`/`cache_file_globs()` are allowed to return, validate the new shape inside this same `try` block rather than trusting a third-party plugin to honor an unenforced return-type contract.

A root shared by more than one plugin, watched via `cache_paths()` (not `poll_only_cache_paths()` — that side has its own, separate version of this same bug; see `_poll_only_root_known_plugins`'s own paragraph further below), has the identical gap `_poll_only_root_known_plugins` was built to close for the poll-only side — just one level earlier, since a WATCHED root's registration ALSO only ever uses whichever contributors happened to succeed AT REGISTRATION TIME. If one plugin's `cache_paths()` call succeeds while another sharing the same root is still failing, `_reschedule_missing_watch()`'s own one-time `_backfill_scan()` only ever globs and reports the healthy plugin's own contribution — the failing plugin's pre-existing artifacts (matched only by ITS globs) are never scanned at all. Once the failing plugin recovers, `_rescan_cache_paths()`'s main loop skips the root outright via its own `if d in self._cache_root_watches: continue` guard — by design, that guard exists to avoid re-registering an already-live watch — so nothing ever re-backfills it, and the recovering plugin's own pre-existing content is silently and PERMANENTLY lost, not just delayed: no later pass ever revisits a root already in `watches`. Confirmed empirically (zero events for such an artifact across an initial registration and several later rescans). Live classification is NOT the gap here — `_classify_cache_path()` already tries every registered plugin regardless of which one's glob matched (see that function's own docstring), so once the recovering plugin's call starts succeeding again, ITS OWN brand-new artifacts are correctly detected by the live watch with no code change needed; only its PRE-EXISTING content (created before this watch's live coverage began) needed a fix.

The fix mirrors the poll-only-side one in spirit but not in mechanism, since a watched root has no recurring poll to naturally retry from — it needed its own explicit catch-up step. `_TrackedWatch` gained two new fields: `known_plugins: frozenset[str]` (every plugin ever recorded as a successful contributor to THIS registration) and `known_content: _RootBaseline | None` (a snapshot of everything this watch's merged globs matched as of the end of the last backfill scan run for it — its own initial registration scan, or a later catch-up). `_discover_cache_dirs()` now returns `owning_plugins` alongside its dirs list (previously discarded — see the `_discover_dirs_by()` paragraph above), and `_rescan_cache_paths()` passes both into a new method, `_backfill_new_contributors()`, called unconditionally on every rescan pass (unlike the main "no live watch yet" loop, this one explicitly targets roots that already ARE in `watches`). For each such root, it compares `owning_plugins.get(d, frozenset())` this pass against `tracked.known_plugins`; a plugin present now that wasn't recorded before is a genuinely new or recovering contributor, and the root gets one more `_backfill_scan()` call — using the FULL merged `globs` list (there's no per-glob ownership recorded, only per-root — see `_discover_cache_dirs()`'s own docstring on why keeping only the first plugin's patterns would be wrong — so isolating "only the new contributor's own patterns" from a root with more than one contributor isn't possible), excluding `tracked.known_content`. Anything already accounted for (backfilled at registration, or observed live since) is still on disk with an unchanged identity and so is present in `known_content` and gets excluded, exactly like `_known_root_exclude()`'s baseline excludes registration-time content for the "no live watch yet" case; only a path genuinely absent from it — the recovering contributor's own pre-existing artifacts, which nothing has ever scanned before now — falls through and gets classified. `known_content` is refreshed to a fresh post-scan snapshot afterward, so a LATER contributor recovering still further doesn't replay what this scan already accounted for, and `known_plugins` is updated to include the newly-seen contributor so this same root isn't flagged again next pass. This deliberately does NOT reuse `_known_cache_roots`/`_known_root_exclude()` — those exist for the "no live watch yet" registration-retry case, a different problem from "the watch already exists but one of its contributors hasn't been backfilled yet."

`_backfill_new_contributors()`'s `_backfill_scan()` call must run directly, synchronously on the event loop thread — NOT via `asyncio.to_thread()`, unlike the `_snapshot_root_baseline()` call right next to it in the same method (that one only reads the filesystem and returns a value, the same reasoning `_known_root_exclude()`'s own `_snapshot_root_baseline()` call and `_poll_cache_dirs_sync()`'s off-thread walk rely on — see their own paragraphs above). An earlier version of this method wrapped `_backfill_scan()` in `asyncio.to_thread()` too, copying that same "avoid blocking the loop for a slow glob walk" pattern onto it without noticing a real difference: `_backfill_scan()` calls `self._queue.put_nowait()` directly for every match it finds (see that method's own docstring), rather than returning plain data for the caller to enqueue back on the loop thread the way `_poll_cache_dirs_sync()` does. `asyncio.Queue.put_nowait()` is not thread-safe to call from a different OS thread than the event loop's — see `_poll_cache_dirs()`'s own docstring for the established pattern this violated (`_Handler`'s watchdog-observer-thread callbacks use `run_coroutine_threadsafe()` for the identical reason). `_reschedule_missing_watch()`'s own, original `_backfill_scan()` call has always run this same way, synchronously on the loop thread — this new call just needed to match it. If `_backfill_scan()`'s own glob walk ever needs to move off-thread for performance, it must first be split the same way `_poll_cache_dirs_sync()` was (return events/identities as plain data, let the caller do the actual queue and `backfill_dedup` mutation on the loop thread) — not wrapped in `asyncio.to_thread()` as-is, which was tried and confirmed unsafe. Verifying this doesn't rely on asserting queued output, since a `put_nowait()` race doesn't reliably corrupt a small, single-artifact test's results — the regression test instead records which OS thread `_backfill_scan()` actually executes on and asserts it matches the caller's own thread.

`_backfill_scan()`'s per-glob `except Exception: log.warning(...)` (see its own docstring, and `_snapshot_root_baseline()`'s identical reasoning above) used to just log a failed pattern and move on with NO signal to either caller — `_reschedule_missing_watch()` and `_backfill_new_contributors()` both then unconditionally treated the scan as fully complete: `_reschedule_missing_watch()`'s own callers (`start()`, `_rescan_cache_paths()`) set `tracked.known_plugins` regardless, and `_backfill_new_contributors()` refreshed `tracked.known_content`/updated `known_plugins` the same way. Whatever ONLY the failed pattern would have matched was therefore never classified or queued by THIS call — but `tracked.known_content`'s own, SEPARATE `_snapshot_root_baseline()` snapshot (a different `glob()` call, taken moments later) can succeed independently even when `_backfill_scan()`'s own call for the identical pattern just failed (a transient error needn't repeat), so it silently absorbed that same pre-existing content into "already accounted for" — permanently missed, since nothing else ever re-backfills a root already in `watches`, and a live watch only ever fires for genuinely NEW creation, never content it never observed to begin with. Confirmed empirically (a pre-existing malicious wheel, matched only by a pattern that failed during registration's own backfill scan, was never reported at all — not even on a later rescan).

`_backfill_scan()` now returns `bool` — `True` only if every glob pattern was scanned to completion, `False` if at least one raised and had to be abandoned. `_reschedule_missing_watch()` itself now also returns `bool` (propagating `_backfill_scan()`'s own result, and additionally `False` if the watch was never even registered — a caller only needs "trust this as complete" vs. "don't," not the reason), and its own two callers (`start()`, `_rescan_cache_paths()`) only set `tracked.known_plugins` when that return is `True` — left unset (at its default, empty `frozenset()`) otherwise, so `_backfill_new_contributors()` correctly still sees every one of this root's CURRENT owning plugins as "new" (not yet in `known_plugins`) on the very next rescan pass, retrying the exact same backfill rather than silently trusting a partial one. `_backfill_new_contributors()` applies the identical gate to its OWN `_backfill_scan()` call: `tracked.known_content`/`known_plugins` are only updated when that pass's scan returned `True`; an incomplete one is logged and left alone for the same next-pass retry. `_reschedule_missing_watch()`'s own post-scan `known_content` snapshot is now also skipped entirely (not just left at whatever it already was) when `_backfill_scan()` itself returned `False` — taking it anyway would reopen the exact bug being fixed, since that separate snapshot call can succeed even when the scan's own identical-pattern call just failed.

This also surfaced a second, independent gap while fixing the first: `_backfill_new_contributors()`'s own `_backfill_scan()` call had no `try/except` around it at all (unlike `_reschedule_missing_watch()`'s belt-and-braces one), even though `_backfill_scan()` already guards its own body and so shouldn't raise in practice — confirmed to matter once a test mocked `_backfill_scan()` directly (bypassing its own internal robustness) and the resulting `RuntimeError` propagated straight out of `_rescan_cache_paths()`, which runs inside `events()`'s own loop body and would have killed the whole cache-monitor consumer task. Given the identical belt-and-braces treatment as the other call site. Note that a single `_rescan_cache_paths()` pass can now call `_backfill_scan()` for the SAME root TWICE: the main loop's own registration call (via `_reschedule_missing_watch()`) first, and — if that one came back incomplete, leaving `known_plugins` unset — `_backfill_new_contributors()`'s own same-pass retry immediately after, since it runs unconditionally right after the main loop in every `_rescan_cache_paths()` call. A test asserting `_backfill_scan()`'s call count for a failure scenario must account for both call sites, not just the registration one.

`_seed_poll_only_baseline()` ignoring the `failed` flag from its own `_discover_poll_only_cache_dirs()` call — on the same "nothing to lose, this root just isn't seeded yet" reasoning `_discover_cache_dirs()`'s callers correctly rely on above — was itself a bug: that reasoning only holds for a consumer that never wholesale-replaces, and `self._poll_only_seen` IS wholesale-replaced, per root, by `_poll_cache_dirs()`. A root a plugin failed to report during this ONE-TIME startup call gets no `self._poll_only_seen` entry at ALL, not merely a stale one `discovery_failed`/`incomplete_roots` handling (two paragraphs below) could later merge against — those mechanisms only ever merge with whatever's ALREADY recorded, and there is nothing recorded for a root that was never seeded in the first place. Once the plugin recovers and that root appears in a real `_poll_cache_dirs()` poll for the first time, it is indistinguishable from a root that's genuinely new this session, and its entire pre-existing contents (from before the daemon even started) replay as brand-new install events — confirmed empirically (a pre-existing wheel fired twice, once per its dual version-dir/`.whl` classification, purely because its root's plugin transiently failed during startup seeding). The mechanism that closes this is `CacheMonitor._poll_only_ever_cleanly_discovered: set[Path]` — see its own paragraph below for why this is a PER-ROOT set, not the single whole-daemon `bool` an earlier version of this fix used and had to be corrected away from.

`_poll_only_ever_cleanly_discovered` records every poll-only root that has EVER appeared in a discovery pass (`_seed_poll_only_baseline()`'s own, or a later `_poll_cache_dirs()`'s — both call the identical `_discover_poll_only_cache_dirs()`) where THAT ROOT'S OWN contributing plugin call(s) succeeded — including a pass where the root's directory didn't exist on disk yet, as long as the plugin CALL itself didn't raise. `_poll_cache_dirs()` computes `unseeded_roots` from it (every root this pass's `cache_dirs` mentions that's NOT yet in this set) and passes that into `_poll_cache_dirs_sync()`, which records such a root's snapshot as normal (finally seeding it, silently) but does NOT append its entries to `events` — exactly the same "record but don't report" treatment `_seed_poll_only_baseline_sync()` itself gives a root's pre-existing contents at real startup. The update to this set is deliberately UNCONDITIONAL over every root `cache_dirs` mentions — `self._poll_only_ever_cleanly_discovered.update(d for d, _ in cache_dirs)`, with NO `if not failed:`/`if not discovery_failed:` guard — because a root's mere presence in `cache_dirs` at all already proves its own plugin call succeeded THIS pass (`_discover_dirs_by()` only ever contributes a plugin's paths when that plugin's own call didn't raise; a raising plugin contributes nothing, for itself or anything it owns). An EARLIER version of this exact fix gated the update on the whole-pass flag anyway and it was empirically confirmed broken by doing so — see the "healthy root, unrelated broken plugin" paragraph below for that failure mode and why the guard had to go. If you touch `_seed_poll_only_baseline()`, `_poll_cache_dirs()`, or `_poll_cache_dirs_sync()` again, re-verify with a reproduction where the SAME plugin fails only on its very first (startup) call and succeeds thereafter — a discovery failure confined to a LATER `_poll_cache_dirs()` call alone doesn't exercise this path, since by then a real baseline already exists for `discovery_failed`/`incomplete_roots` to merge against.

The very first version of the fix above used a single global `CacheMonitor._poll_only_seed_incomplete: bool` (`True` from construction, cleared to `False` only once a discovery pass reported EVERY registered plugin succeeding) instead of the per-root set — `_poll_cache_dirs()` suppressed events for any root with no prior `self._poll_only_seen` entry for as long as this ONE flag stayed `True`, anywhere in the daemon. This conflated "this SPECIFIC root's own seeding might still be incomplete" with "SOME plugin, anywhere, is currently failing": a perfectly healthy plugin's own poll-only root (e.g. a Python `sdists-v*` directory a real `uv sync` creates for the first time this session) had its own first, genuinely new artifacts silently swallowed as "possibly stale startup content" for as long as an entirely UNRELATED plugin kept failing — and for a plugin that never recovers (a genuine bug in that plugin, not a transient glitch), this was PERMANENT, not merely delayed, for the rest of the daemon's uptime. Confirmed empirically: a healthy root's very first sighting — with a genuinely malicious first-ever install already in it — produced zero events regardless of how many later polls ran, solely because a different, unrelated plugin's `poll_only_cache_paths()` never stopped raising. Switching to the per-root `_poll_only_ever_cleanly_discovered` set (above) closes this without reopening the original startup-recovery bug it replaces, since a root's OWN clean discovery is now tracked independently of any other root's plugin's health. A naive per-root fix using `self._poll_only_seen` membership alone (rather than this dedicated set) was ALSO tried and confirmed broken by an existing, unrelated test: a root whose directory simply doesn't exist yet also has no `self._poll_only_seen` entry, even though its plugin call has been succeeding the whole time, and its later, genuinely first appearance must be reported normally — not suppressed as though it might be pre-existing content a past failure missed. If you touch this mechanism again, verify BOTH directions with a reproduction: (1) a root whose OWN plugin failed at startup and recovers later must still have its pre-existing content suppressed on that first recovery poll, and (2) a root whose OWN plugin has always succeeded must report its first-ever content immediately, even while a completely different, permanently-broken plugin exists in the same daemon.

`_poll_only_ever_cleanly_discovered` populated PURELY from roots that have appeared in some PAST discovery pass — the version described above — still had its own gap: it can only ever add a path that was actually IN `cache_dirs` at least once, but every real `poll_only_cache_paths()` implementation (`PythonLanguage`'s own, via `p.is_dir()`) filters to EXISTING directories, so a versioned cache root (uv's `sdists-v*`) that hasn't been created yet on THIS machine is simply absent from every PAST pass's `cache_dirs`, no matter how many of them ran cleanly — there is no prior pass to have added it from. Once uv genuinely creates that root for the first time and an install lands in it, `_poll_cache_dirs()`'s own "not yet in `_poll_only_ever_cleanly_discovered`" check still finds it absent and wrongly suppresses its first-ever content, indistinguishable from the original startup-recovery bug this whole mechanism exists to fix — confirmed empirically, but ONLY with the REAL, unmodified `poll_only_cache_paths()` hook: every earlier regression test for this mechanism overrode it with an unconditional `lambda: [sdists_root]`, which reports that path regardless of whether it exists and therefore could never exercise this gap — a review finding caught what the existing test suite structurally could not. The fix adds a second, complementary signal: `CacheMonitor._poll_only_ever_succeeded_plugins: set[str]` — the `name` of every plugin whose OWN `poll_only_cache_paths()`/`cache_file_globs()` call has EVER completed without raising, across the whole daemon session, populated the same unconditional way as `_poll_only_ever_cleanly_discovered` (a plugin's call succeeding this pass, independent of `discovery_failed` from some OTHER plugin). `_discover_dirs_by()` now also returns `owning_plugins: dict[Path, frozenset[str]]` (which plugin(s) actually contributed each returned path this pass) alongside `succeeded_plugins: frozenset[str]` (which plugins' own calls didn't raise this pass); `_poll_cache_dirs()`'s `unseeded_roots` now excludes a root — i.e. reports it normally even on its first-ever appearance — if EVERY plugin in `owning_plugins.get(d, frozenset())` is already in `self._poll_only_ever_succeeded_plugins`, since a plugin with a fully clean call history could never have hidden that root's pre-existing content behind an exception: its absence from every earlier pass is proof of non-existence, not proof of a miss. A plugin is trusted permanently once it has one clean call, even if a LATER call from the same plugin fails — that later failure's own effect on state freshness is still separately handled by `discovery_failed`'s per-poll merge logic and `_poll_only_seed_incomplete_roots` (two paragraphs above), not by retroactively un-trusting roots that plugin already safely reported. If you touch `_discover_dirs_by()`, `_discover_poll_only_cache_dirs()`, `_seed_poll_only_baseline()`, or `_poll_cache_dirs()` again, re-verify with the REAL `poll_only_cache_paths()` hook (not a lambda override) that a genuinely new versioned root's first-ever install is reported, not just with a mocked one.

`_poll_only_ever_cleanly_discovered` only protects a root with NO `self._poll_only_seen` entry at all — it has its own gap, one level narrower, for a root that DOES get an entry from `_seed_poll_only_baseline()` but only a PARTIAL one: `_seed_poll_only_baseline_sync()`'s per-glob-pattern `try/except` (mirroring `_poll_cache_dirs_sync()`'s own — see that method's `incomplete_roots` paragraph above) logs and moves on if one glob pattern raises partway through its results, but used to record `baseline[cache_dir]` — built from whatever the OTHER patterns managed to yield — as if it were the root's complete pre-existing contents regardless. Since `poll_only_cache_paths()`/`cache_file_globs()` themselves succeeded (discovery isn't what failed here — one glob pattern INSIDE an otherwise-successful walk is), the root correctly lands in `_poll_only_ever_cleanly_discovered` — but that leaves nothing protecting this root's still-incomplete `self._poll_only_seen` entry: it already has an entry, so `_poll_cache_dirs()`'s "not yet in `_poll_only_ever_cleanly_discovered`" `unseeded_roots` check doesn't catch it either. Once the transient glob failure clears on the very next real `_poll_cache_dirs()` poll, the artifact only the failed pattern would have found replays as a brand-new event — confirmed empirically (a pre-existing wheel matched only by a failed `**/*.whl` pattern during startup seeding fired as new once that pattern started working again). The fix is `CacheMonitor._poll_only_seed_incomplete_roots: dict[Path, float]` (empty from construction) — `_seed_poll_only_baseline_sync()` now also returns `incomplete_roots` (identical meaning to `_poll_cache_dirs_sync()`'s own), and `_seed_poll_only_baseline()` records each of those roots into this dict unconditionally (independent of whether the root also lands in `_poll_only_ever_cleanly_discovered` the same call) — the two are independent signals for independent failure classes. A root is removed once its OWN pass completes without landing back in `incomplete_roots` — at which point `current_snapshot[root]`, unioned with whatever `self._poll_only_seen` already had via `still_present`'s own identity carry-forward, is finally a genuinely complete accounting.

The value stored per root is that seed walk's own `cutoff` (the same margin-adjusted `time.time()` snapshot `_seed_poll_only_baseline_sync()` uses), and it is load-bearing, not bookkeeping. An earlier version stored only the root (a bare `set[Path]`) and folded it into the SAME `unseeded_roots` set passed to `_poll_cache_dirs_sync()`, giving a partially-seeded root the identical WHOLE-root event-suppression treatment as a never-seeded one. That was itself a bug — and, as a later review round established, the reasoning that made it look acceptable ("whole-root suppression is right for a root nothing has ever successfully walked") was ITSELF wrong, for the same reason, in all three arms: an artifact created AFTER the point coverage was lost has no other observer at all, since a poll-only root is never watched by design, so suppressing it ALSO recorded it into `current_snapshot` (which becomes the new baseline) and it was therefore emitted on NO poll, ever. Confirmed empirically (a genuinely new sdist landing in that window produced zero events across the recovery poll and every later one). `_poll_cache_dirs()` therefore passes these cutoffs to `_poll_cache_dirs_sync()` as a separate `seed_incomplete_cutoffs` argument rather than merging them into `unseeded_roots`, and suppression for such a root applies only to an entry whose own `st_mtime` is strictly before its cutoff; ties and unreadable mtimes fall on the REPORT side, matching `_seed_poll_only_baseline_sync()`'s own bias. If you touch this, verify BOTH directions — genuinely pre-existing content must stay suppressed on the recovery pass (that is what `first_poll == []` asserts in `test_poll_cache_dirs_does_not_replay_partially_seeded_root`) AND an artifact created after the failure must still be reported (`test_incomplete_seed_recovery_still_reports_artifact_created_after_the_failure`); a fixture representing "pre-existing" must be backdated via the `_backdate()` helper, since content created with no delay before `start()` falls inside the cutoff's safety margin. If you touch either sync scanner's per-pattern `try/except` again, keep both `incomplete_roots` returns and both the whole-discovery-call and per-root incomplete trackers — collapsing "discovery itself failed" and "one pattern inside an otherwise-fine walk failed" back into a single signal reopens whichever of these two bugs the collapse loses.

**Every poll-only suppression arm must be mtime-scoped — there are THREE, and only one of them originally was.** A later review round found the same permanent-miss bug still live in the other two: `unseeded_roots` (a root this daemon has never cleanly discovered) and `root_unseeded_globs`/`_poll_only_pending_reseed_globs` (a contributor that has never had a successful walk of its own globs here) both suppressed UNCONDITIONALLY, while still recording the entry into `current_snapshot`. Confirmed empirically for both: with a plugin whose `poll_only_cache_paths()` raises once during `start()`'s seed, a malicious artifact installed *well after* daemon startup produced zero events across every subsequent poll, and was absorbed into the baseline — a permanent silent miss of a real install, which is the exact security failure this tool exists to prevent. The trigger is only a transient plugin/glob failure at startup, but the consequence is unbounded in time. `CacheMonitor._poll_only_startup_cutoff` (captured in `start()` before any discovery or seeding runs, margin-adjusted by `_SEED_BASELINE_CUTOFF_SAFETY_MARGIN_SECONDS`) now scopes those two arms, exactly as the per-root `seed_incomplete_cutoffs` scopes the first. The general rule: **suppression may only ever withhold content that predates the moment coverage of that root was actually lost**, because a poll-only root has no live watch to catch anything created afterwards, and the suppressing pass is also the pass that baselines it. Note `startup_cutoff` is EXACT for `unseeded_roots` (coverage there really was lost at daemon start) but deliberately CONSERVATIVE for `root_unseeded_globs`, whose contributor may only start sharing the root — or recover — mid-session: its true "coverage lost" moment is later than startup, so this bound suppresses strictly LESS than a per-contributor cutoff would. That errs the safe way (the contributor's pre-daemon backlog is still suppressed; an artifact created between startup and its recovery is reported rather than withheld), and tightening it would trade an occasional duplicate for a potential permanent miss. Do not "fix" that asymmetry without re-verifying both directions empirically. Regression coverage: `test_unseeded_root_still_reports_artifact_created_after_startup` and `test_pending_reseed_globs_still_report_artifact_created_after_startup` (both assert the new artifact IS reported and that genuinely pre-daemon content, backdated via `_backdate()`, is still suppressed). If you add a FOURTH suppression signal here, give it a cutoff too — an unscoped one is a permanent miss, not a delay.

**A cutoff must be sourced from the moment the daemon started, never re-read later in the same startup path.** `_seed_poll_only_baseline()` originally took its own `time.time()` AFTER `_discover_poll_only_cache_dirs()` returned. That hook calls third-party plugin code (`poll_only_cache_paths()`, `cache_file_globs()`) and can take real time, so the resulting cutoff was LATER than the moment the daemon actually began — and an artifact that landed while discovery was still running had an mtime safely before it, so `_seed_poll_only_baseline_sync()` recorded it into the baseline as pre-existing. A poll-only root is never watched, so nothing else ever observes that artifact, and every later poll only reports what is NOT already in the baseline: the install was reported on no poll, ever. Confirmed empirically (zero events across every subsequent poll for an artifact created at the start of a slow discovery hook); `test_seed_baseline_reports_artifact_created_during_slow_discovery` pins it. The seed now reuses `self._poll_only_startup_cutoff`, falling back to a fresh reading only when `start()` never ran. Note the failure is ordering-sensitive and easy to mis-analyse: an artifact landing at the END of discovery has an mtime AFTER even the late cutoff and is correctly excluded, so only the early-in-discovery window actually loses the install — a reproduction must place the artifact before the slow part, not after it.

`_poll_only_ever_cleanly_discovered` and `_poll_only_ever_succeeded_plugins` both operate at the granularity of "has this root/plugin EVER succeeded," which has its own gap distinct from every failure mode above: a root shared by TWO plugins, each contributing its own distinct glob pattern, where one plugin succeeds during the very FIRST discovery pass (`start()`'s `_seed_poll_only_baseline()`, or an early `_poll_cache_dirs()` poll) while the other fails. The root still lands in `cache_dirs` (from the healthy plugin alone) and gets marked into `_poll_only_ever_cleanly_discovered` from that one pass — correctly, by that set's own unconditional-update design (see its paragraph above) — but only the healthy plugin's glob was ever actually walked; the failing plugin's own pre-existing artifacts (matched only by ITS glob) were never seeded into `self._poll_only_seen` at all. Once the failing plugin finally recovers, the root's `_poll_only_ever_cleanly_discovered` membership is already `True`, so `_poll_cache_dirs()`'s "not yet cleanly discovered" `unseeded_roots` check no longer catches it — the recovering plugin's genuinely pre-existing content replays as a brand-new install the moment its glob first runs successfully, confirmed empirically. Neither `_poll_only_ever_cleanly_discovered` (per-root, not per-contributor) nor `_poll_only_ever_succeeded_plugins` (global per-plugin, not root-scoped — a plugin trusted from succeeding on some OTHER root would wrongly exempt a DIFFERENT shared root it hasn't actually walked yet) covers this: clean-seed state has to be tracked per root AND per contributing plugin.

The fix adds `CacheMonitor._poll_only_root_known_plugins: dict[Path, frozenset[str]]` — for each root, the set of plugin names EVER recorded as a successful contributor TO THAT ROOT specifically — and a new method, `_roots_with_a_new_contributing_plugin(cache_dirs, owning_plugins)`, called ONLY from `_poll_cache_dirs()` (never from `_seed_poll_only_baseline()` — see below for why), which returns `(needs_reseed, unseeded_globs)`: `needs_reseed` is the subset of roots that are (a) already in `_poll_only_ever_cleanly_discovered` (i.e. NOT this root's first-ever appearance) AND (b) have at least one contributing plugin this pass that wasn't already recorded as a known contributor for that specific root; `unseeded_globs` maps each such root to the UNION of just the new/recovering contributor(s)' OWN `cache_file_globs()` patterns (re-queried directly from those specific plugin objects, not reused from `cache_dirs`' own merged, all-contributors glob list for that root).

`_poll_cache_dirs()` does NOT fold `needs_reseed` into `unseeded_roots` (whole-root suppression) — only `unseeded_globs` is used, checked per-glob-pattern inside `_poll_cache_dirs_sync()`'s classify loop (`glob in unseeded_globs.get(cache_dir, frozenset())`), not per-root. An earlier version folded `needs_reseed` into `unseeded_roots` directly, which was itself a real, confirmed-empirically bug: `unseeded_roots` gates `_poll_cache_dirs_sync()`'s reporting for EVERY glob pattern under that root, not just the recovering contributor's own — so a genuinely new artifact from the ALREADY-known, healthy contributor, if it happened to appear on the exact same pass a different contributor recovered, was ALSO silently recorded into `current_snapshot` without being reported. Since `self._poll_only_seen` is wholesale-replaced from `current_snapshot` every pass (not merged), this wasn't merely a delay: that artifact's entry, once silently recorded, made every LATER poll treat it as already-seen too — a permanent, silent miss, indistinguishable from any other artifact this whole mechanism exists to correctly report. `still_present`'s own identity carry-forward does NOT rescue this case — it only carries forward entries already present in a PRIOR poll's `self._poll_only_seen`, never a genuinely new entry appearing on the SAME pass the suppression is active. If you touch `_roots_with_a_new_contributing_plugin()`, `unseeded_globs`, or its consumption in `_poll_cache_dirs_sync()` again, re-verify with a reproduction where a genuinely new artifact from an ALREADY-known contributor is created on the SAME poll a different contributor first recovers — it must still be reported on that same pass, not merely on some later one.

`_poll_cache_dirs_sync()`'s per-glob suppression check (previous paragraph) had a further, order-dependent bug when two plugins legitimately share a root AND their glob patterns overlap on the same path (e.g. an established plugin's narrow `pypi/*` and a recovering plugin's broad `**/*` both matching the same artifact) — a real, intentionally-supported scenario, not hypothetical (see `_discover_cache_dirs()`'s own docstring: "Two plugins can legitimately return the same cache_paths() entry"). The original loop walked one glob pattern at a time, and the instant ANY pattern matched a path it added that path to `globbed` and skipped re-evaluating it for every subsequent pattern — so whichever pattern happened to be iterated first permanently decided suppression for that path, regardless of whether another, non-suppressed pattern would also have matched it. Iteration order of `globs` is the union-merge order from `_discover_dirs_by()` (plugin-registration order), an implementation detail, not a contract — so if the recovering contributor's suppressed, broader pattern happened to be walked before the established contributor's own narrower pattern also matching the identical path, the path was recorded into `current_snapshot` without an event, and the established contributor's genuinely new artifact was silently never reported. Confirmed empirically with a reproduction using two plugins sharing a root, registered in the order that put the suppressed/broad glob first. The fix restructures the loop into two passes: first, `matched_by: dict[Path, set[str]]` collects, for every path, the FULL set of glob patterns (across all contributors) that match it; second, each path is classified once and suppression is decided from `matching_globs <= root_unseeded_globs` — i.e. suppressed only if EVERY matching pattern is itself in the suppressed set, so a path matched by at least one established (non-suppressed) contributor's pattern is always reported, independent of iteration order. If you touch this classify loop again, re-verify with a reproduction where the suppressed/recovering contributor's glob is registered (and therefore walked) BEFORE the established contributor's own overlapping glob — a single-pass, first-match-wins structure will silently reintroduce this exact order dependency even if it looks like a harmless refactor.

`_backfill_scan()` (the WATCHED-root counterpart to the poll-side loop above) had its own, different first-match-wins bug in the same `globbed` set — not about suppression order, but about CLASSIFICATION RETRY. It marked a path in `globbed` BEFORE attempting classification, so a path matched by several of the merged patterns was only ever attempted under whichever one was visited first. `_classify_cache_path()` catches a raising plugin, logs it, and returns `None` — indistinguishable at that call site from "no plugin recognises this" — so a TRANSIENT failure (a plugin parsing a still-being-written file; `NodeLanguage.classify_cache_file()` really does open and json-parse an index-v5 entry, so this is reachable rather than theoretical) also skipped every later overlapping pattern for the same path. For PRE-EXISTING content there is no live creation event left to fall back on, so that was a permanent miss. Confirmed empirically (one classification attempt, zero events; with the fix, two attempts and one event). `globbed` is now recorded only AFTER classification succeeds — matching the reasoning already documented for `backfill_dedup.claim()` immediately below it in the same method — so a failed attempt stays retryable while a successful one is still queued exactly once no matter how many patterns match it. A path skipped by `effective_exclude` IS still recorded, since that decision is deterministic and would reach the same answer under any other pattern. If you touch this loop, keep BOTH properties covered by a reproduction: a transiently-failing classification must be retried by the next overlapping pattern, and a successfully classified path must still produce exactly one event across all matching patterns.

`_roots_with_a_new_contributing_plugin()` originally scoped `unseeded_globs` by calling a new/recovering contributor's `cache_file_globs()` a SECOND time, even though that exact plugin's identical call had already succeeded moments earlier the SAME pass, inside `_discover_dirs_by()` — that success is exactly what makes the plugin appear in `owning_plugins`/`new_plugins_by_root` in the first place, so the second call was always redundant on any pass that reaches it. If that second, purely-redundant call transiently raised (a plugin already known to be capable of failing, or an ordinary transient I/O blip), `unseeded_globs` for that root got no patterns from it, so `_poll_cache_dirs_sync()`'s classify loop didn't suppress anything for that contributor — its genuinely pre-existing artifacts were reported as brand-new installs. Worse than a one-poll miss: `_poll_only_root_known_plugins[d]` is updated unconditionally, BEFORE this glob lookup even runs (`known | this_pass`), to include the plugin as a fully-known contributor regardless of whether the lookup below it succeeds — so a root whose only glob-lookup attempt failed here was never flagged as needing reseed again on any LATER pass either, permanently losing the one chance to suppress that stale content. Confirmed empirically with a reproduction where `cache_file_globs()` succeeds on `_discover_dirs_by()`'s own call and then raises only on this method's separate, later call in the same pass.

The fix removes the second call entirely rather than adding a fallback for its failure: `_discover_dirs_by()` now also returns `globs_by_plugin: dict[str, frozenset[str]]` — each successful plugin's OWN `cache_file_globs()` result from that exact call, alongside the `dirs`/`failed`/`succeeded_plugins`/`owning_plugins` it already returned — and `_roots_with_a_new_contributing_plugin()` takes this as a new parameter and reuses it directly instead of re-invoking the hook. A plugin absent from `globs_by_plugin` can only mean its ONE call, inside `_discover_dirs_by()` itself, already failed that pass — which is exactly the pass where `owning_plugins` (and so `new_plugins_by_root`) wouldn't include it either, so there's no case where this method needs a glob result it wasn't handed. `_discover_cache_dirs()` discards `globs_by_plugin` the same way it already discards `failed`/`succeeded_plugins` (see that method's own docstring) — it has no caller that needs per-plugin glob results, only `_discover_poll_only_cache_dirs()`'s consumer (`_poll_cache_dirs()`) does. If you add a third caller of `_discover_dirs_by()` that needs to scope suppression or backfill to a SPECIFIC plugin's own patterns, thread `globs_by_plugin` through to it the same way rather than re-calling `cache_file_globs()` — that shape has now caused a real, confirmed-empirically bug once.

`_seed_poll_only_baseline()` deliberately does NOT call `_roots_with_a_new_contributing_plugin()` — it only unconditionally records `owning_plugins` into `_poll_only_root_known_plugins` (`known | this_pass`, no reseed comparison). Calling the helper there was tried first and confirmed wrong: `_poll_only_root_known_plugins` starts completely empty at construction, so at startup EVERY root discovered would look like "a contributor not yet known for this root" purely from having no prior recorded state — wrongly flagging every root as needing reseed on its own very first pass, which would suppress that root's FIRST real `_poll_cache_dirs()` poll afterward, including genuinely new content arriving in the gap between startup and that poll.

The `d in self._poll_only_ever_cleanly_discovered` guard inside `_roots_with_a_new_contributing_plugin()` is likewise not redundant — omitting it was tried and broke `test_new_poll_only_root_reported_using_the_real_unmodified_discovery_hook` (a regression test from an earlier fix in this same area, using the REAL, unmocked `PythonLanguage.poll_only_cache_paths()` hook, not a lambda override): a root's own genuine first-ever appearance in `_poll_cache_dirs()` is already correctly exempted from suppression by the EARLIER, separate `unseeded_roots` checks (via `_poll_only_ever_cleanly_discovered` or `_poll_only_ever_succeeded_plugins`), but without this guard it would ALSO look like "a contributor not in `_poll_only_root_known_plugins` yet" the very first time the helper ever sees that root, since that dict starts empty for every root too — wrongly suppressing a single-plugin root's first-ever, non-shared install. If you touch this mechanism again, verify with a reproduction covering all three cases: a shared root where one plugin succeeds and the other recovers later must suppress only the recovering plugin's own pre-existing content (not replay it, and not suppress the already-trusted plugin's own new content); a non-shared root's genuine first-ever appearance must still report normally; and a root already fully known to both plugins must never be flagged for reseed at all.

`_roots_with_a_new_contributing_plugin()` marks a contributor known for a root — `self._poll_only_root_known_plugins[d] = known | this_pass` — as soon as it appears in `owning_plugins`, which is BEFORE that contributor's globs have actually been walked (the helper runs at the top of `_poll_cache_dirs()`; the walk happens later, in `_poll_cache_dirs_sync()`). That left a gap: if one of the new/recovering contributor's own globs RAISES during the very recovery pass meant to seed it (a transient I/O error on part of a large tree — `_poll_cache_dirs_sync()`'s per-pattern `try/except` logs and moves on), only THAT pass suppressed its artifacts via `unseeded_globs`. By the next pass the contributor is already recorded as known, so `_roots_with_a_new_contributing_plugin()` no longer flags it, nothing populates `unseeded_globs` for it, and its never-walked, genuinely pre-daemon artifacts replay as brand-new installs the moment the glob starts working. Confirmed empirically (a pre-daemon `.tar.gz` matched only by the recovering plugin's own glob fired as a fresh install on the pass after the failing one). Note `_poll_only_seed_incomplete_roots` does NOT cover this: it is only ever unioned into from `_seed_poll_only_baseline()` (the startup path), never from `_poll_cache_dirs()`, which only ever subtracts from it.

The fix is `CacheMonitor._poll_only_pending_reseed_globs: dict[Path, frozenset[str]]` — per root, the new/recovering contributor's own glob patterns whose reseed walk has not yet completed cleanly. `_poll_cache_dirs()` unions each pass's freshly-returned `unseeded_globs` INTO this dict and then passes the whole dict (not just this pass's own result) to `_poll_cache_dirs_sync()`, and drops a root's entry only once that root appears in `cache_dirs` and NOT in `incomplete_roots` — i.e. only once a pass genuinely walked it to completion, at which point the contributor's pre-existing artifacts are really recorded in `current_snapshot` and no later pass has anything left to replay. This deliberately does NOT reuse `_poll_only_seed_incomplete_roots`, despite an earlier version of `_poll_only_root_known_plugins`'s own docstring describing exactly that (a design that was documented but never actually implemented — the helper's `needs_reseed` return was simply discarded into an unused `_needs_reseed`): that set feeds `unseeded_roots`, i.e. WHOLE-root suppression, which was separately tried for this case and confirmed to also suppress — and, since `self._poll_only_seen` is wholesale-replaced every pass, permanently lose — a genuinely new artifact from an ALREADY-known, healthy contributor sharing the same root. Suppression here therefore stays scoped to the recovering contributor's OWN patterns. If you touch this mechanism again, verify all four directions with a reproduction: the pre-daemon artifact stays suppressed on the failing recovery pass AND on the pass after the glob recovers; a genuinely new artifact from that same contributor is still reported once its walk completes; and a healthy contributor's own new artifacts are never suppressed at any point.

That merge-on-failure must be done PER ROOT — union the two entry sets — not by replacing `dict.get(root)` wholesale with a top-level `dict.update()`. Two plugins can legitimately share the same poll-only root (see `_discover_cache_dirs()`'s own docstring above), each contributing different globs; if one of them fails, `_discover_poll_only_cache_dirs()`'s result for that shared root only carries the healthy plugin's narrower glob, so `_poll_cache_dirs_sync()`'s `current_snapshot[root]` for that pass can genuinely be missing an entry the failed plugin previously classified. `_poll_cache_dirs_sync()`'s own identity-based carry-forward (`still_present`, built from `self._poll_only_seen.get(cache_dir, set())` regardless of which glob originally matched an entry) already rescues this for a root with an EXISTING baseline — but a shared root discovered for the very first time on the exact same pass a plugin sharing it happens to fail has nothing to carry forward from at all, so `current_snapshot[root]` there is entirely the healthy plugin's narrower result. A plain `merged.update(current_snapshot)` would then install that as the root's complete baseline, permanently losing the failed plugin's own artifacts under that root until they eventually fire as a spurious "new" event once that plugin finally succeeds — confirmed empirically by isolating this merge step from `_poll_cache_dirs_sync()`'s carry-forward (which alone is not sufficient for this exact no-prior-baseline case). The fix is `merged[root] = merged.get(root, set()) | current_snapshot[root]` for every root in `current_snapshot`, not a bare `dict.update()`.

`_poll_cache_dirs_sync()` has a SECOND, narrower way `current_snapshot[root]` can be incomplete, independent of `_discover_dirs_by()`'s whole-pass `discovery_failed`: an individual glob PATTERN for a root that WAS successfully discovered can still raise partway through iterating its own results (a transient I/O error on part of a large tree, not a `cache_file_globs()`/`poll_only_cache_paths()` failure — discovery itself succeeded fine). The per-pattern `except Exception: log.warning(...)` around the glob loop only logged and moved on, leaving `current_snapshot[cache_dir]` — built from whatever the pattern managed to yield before raising, or nothing at all — silently treated as the COMPLETE picture for that root once `_poll_cache_dirs()` wholesale-replaced `self._poll_only_seen[root]` from it, for any root not affected by `discovery_failed`. `_poll_cache_dirs_sync()` therefore also returns `incomplete_roots: set[Path]` (any root whose glob loop raised for at least one pattern), and `_poll_cache_dirs()`'s merge treats a root in `incomplete_roots` exactly like `discovery_failed` treats every root `current_snapshot` mentions: union with the prior baseline instead of trusting it as complete. Confirmed empirically by isolating this from carry-forward with a directly-mocked `current_snapshot`/`incomplete_roots` (a real glob failure alone doesn't discriminate pre/post-fix in an integration test, since `still_present`'s own identity re-check independently rescues most realistic single-poll scenarios — the isolated mock is what actually proves the merge logic itself, not just carry-forward, handles this). If you touch this merge again, keep `discovery_failed` (whole-pass) and `incomplete_roots` (per-root) as two independent triggers for the same union-not-replace treatment — collapsing them back into one flag reopens either this bug or the earlier shared-root one, depending on which direction the collapse goes.

`on_moved()` classifies `event.dest_path` UNCONDITIONALLY, with no containment check against the watch root — which is correct on Linux/inotify but rests on a platform assumption worth knowing. `_Handler` (the live inotify dispatch class) must classify BOTH `on_created()` and `on_moved()`, not just the former — uv's Unix `replace_symlink()`, used whenever a cache key that already exists is being replaced (a same-version reinstall or rebuild landing on an identical `wheels-v*`/`sdists-v*` index entry), creates a fresh temporary symlink and renames it over the destination rather than unlinking and recreating in place. inotify — and watchdog 6 on top of it — reports an atomic rename onto an already-existing path as a single move event (`IN_MOVED_TO`), dispatched to `on_moved()` with the final path as `event.dest_path`, never to `on_created()`, which only fires for the temporary symlink's own creation (and correctly fails classification on that temp name, since it's never a real cache-entry shape). A 200 status does not guarantee a well-formed body, and `batch_query()`'s only `except` is `httpx.RequestError` — so two related malformed-response shapes escaped it entirely: `resp.json()` raises `ValueError`/`JSONDecodeError` on invalid JSON, and a VALID but non-object body (`null`, `[]`, a bare string) makes `_parse_batch_response()`'s own `data.get("results", ...)` raise `AttributeError`. `isinstance(body, dict)` only clears the TOP level, and the nesting below it raises in its own right: `"vulns": null` (TypeError), a vuln with no `"id"` (KeyError), a non-list `"vulns"`, or a field that fails `OsvAdvisory`'s pydantic validation. That placement states the principle but does NOT enforce it — `return_exceptions=True` covers only the FETCH, and a /vulns/{id} call can SUCCEED while returning a body `_extract_fixed_versions()` cannot parse (`affected: [null]`, a non-list `affected`, a null `package`/`ranges`/`events` entry — five shapes confirmed). That guard must be PER RESULT, not one `try` around the whole parse loop — the latter was tried and is a real security regression, not just over-eager degradation. A batch where ONE sibling had a null `"vulns"` degraded EVERY result, discarding a genuine `MAL-` advisory that OSV had plainly returned for a DIFFERENT package. Regression coverage also includes `test_sandbox_gate_still_blocks_when_a_sibling_result_is_malformed`, which pins the downstream consequence rather than just the parser's return.

A per-result guard only catches malformation that RAISES, and an empty non-list `"vulns"` does not: `{}` or `""` iterates zero times and produced an authoritative CLEAN verdict — cached for the full TTL. The general rule: when a zero-iteration loop's result is a verdict, validate the container's type rather than relying on iteration to fail.

**Per-result is still too coarse: a malformed VULN must not cost its siblings, and a degraded result is not necessarily empty.** With one `try` around a result's whole vuln loop, `[{"id": "MAL-1"}, {}]` parsed MAL-1, then the `KeyError` replaced the entire result with an advisory-free degraded one — a real malicious verdict discarded because of the entry beside it. Confirmed empirically. `_parse_vulns()` now parses each vuln independently: every advisory that parses is kept, and any failure marks the result `degraded` (partial — its ABSENCES prove nothing, so it is still never cached and never records a dedup completion). A vuln whose full parse fails but whose `id` is a usable string is kept id-only, with any string `aliases`, because the id and a MAL- alias are exactly what `is_malicious` reads — `affected: [null]` makes `_extract_fixed_versions()` raise, which would otherwise drop a MAL- advisory over its decoration. Keeping the advisories is only half of it: six consumers checked `degraded` BEFORE `has_malicious` and skipped, so the retained verdict still failed open. The four sandbox gates (`_preflight_shell`, `_preflight`, `_scan_updated_lock_files`, `_post_scan`) now check `has_malicious` first; `scan-cache` counts the failure but still alerts; `pa query` prints the advisories with a partial-response warning instead of only "unavailable"; `_run_scan` and the scheduler count the failure but no longer `continue` past it, so the parsed advisories reach `findings`. The daemon already alerted on `has_malicious` regardless of `degraded` and needed no change; pa-central's `findings` > `degraded` status precedence already reports such a scan as `findings`. **The rule for any consumer: act on `has_malicious` before, never instead of, treating a result as unchecked.** Regression coverage: `test_malformed_vuln_keeps_the_advisories_that_parsed` (parser, incl. the id-only and alias cases), `TestGatesBlockOnPartialMaliciousResult` plus `test_sandbox_gate_blocks_on_a_partial_result_with_a_malicious_advisory` (each gate pinned individually — reverting any ONE gate fails exactly its own test), and the `partial` tests for `pa query`, `scan-cache`, `_run_scan_project` and the scheduler. `_fake_osv_context(partial=True)` in `test_sandbox.py` produces such a result. Note `_preflight_shell` calls `scan_project`, not `scan_lockfiles`, so a fixture that patches only the latter never reaches its OSV gate and passes vacuously.

`batch_query()` must return EXACTLY one result per query, in order — that is an invariant every caller relies on, and `_parse_batch_response()` did not hold it. It pairs queries to the response's `results` array with `zip()`, which silently truncates, so a 200 response that was short, missing `results` entirely, or held a non-object element returned FEWER results than queries. Six call sites across `daemon.py`, `cli/app.py` and `sandbox/runner.py` (four) zip the two back together positionally, so a short response mis-attributes one package's verdict to another; worse, for `_process_event()`'s own single-package query it left `osv_result` as `None`, which is neither malicious NOR explicitly degraded — so the evaluation was marked authoritative, a dedup completion was recorded, and every later observation of that install was suppressed exactly like a clean verdict. Confirmed empirically end-to-end: a malformed-but-200 response produced zero alerts for a genuinely malicious package, across the glitch AND after OSV started answering correctly. `_parse_batch_response()` now REJECTS any count mismatch outright — it raises, so `batch_query()` retries the response and degrades every query if it stays malformed. Padding the short tail with `degraded=True` entries was tried first and is WRONG: the batch response carries no per-result identifier (no package name, no index), which is why these are paired positionally at all, so a mismatch destroys the only means of alignment there is and the payload cannot say WHICH entry is missing — "the tail was truncated" and "an earlier element was omitted" are indistinguishable. Padding assumes truncation; if the omission was earlier, every later verdict shifts onto the wrong package, so a malicious advisory is attributed to an INNOCENT package while the genuinely malicious one is marked degraded and never alerted — one malformed response producing both a wrong verdict and a silent miss. Confirmed empirically. Rejecting instead trades that for a "could not be checked" warning, the tradeoff this module makes everywhere else. A response LONGER than the query list is rejected for the same reason: `zip()` silently discarded the surplus, so it went unnoticed despite meaning the response does not correspond to what was asked. A non-dict ELEMENT is still handled per result (degraded, never a clean verdict) rather than invalidating the batch, since that one is positionally unambiguous. Note any test mocking a fixed-size response must match its batch size exactly — two dedup tests drained ONE event per batch against a two-result body and only passed because `zip()` hid the surplus. `_process_event()` additionally treats `osv_result is None` as non-authoritative alongside `degraded` — deliberate defence in depth, not redundancy: with the parser fix alone a regressed parser silently reopens the whole bug, and mutation-testing confirms the test fails only when BOTH are reverted while the `None` check alone still rescues it. Regression coverage: `test_short_results_array_is_padded_with_degraded_results`, `test_missing_results_key_yields_degraded_results`, `test_malformed_result_element_is_degraded_not_fatal`, `test_unanswered_query_does_not_record_a_dedup_completion`.

Not caching a degraded result has a cost that has to be paid back explicitly: it leaves every such entry a CACHE MISS, so `_process_event()`'s own cache-first lookup repeated the entire fully-retried query once per event. Measured for a 50-package batch at `max_retries=3`: **153** HTTP `querybatch` requests (one retried batch, then 50 retried single-package queries) where 3 would do — a 51x amplification aimed at an already-failing service — plus roughly 350s of sequential retry backoff, during which that monitor's `_consume()` task processes nothing at all. `_batch_prefetch()` therefore RETURNS the degraded results it declined to cache, keyed by `(ecosystem, name, version)`, and `_consume()` threads that dict through `_process_claimed_event()` into `_process_event()`, which consults it after the `osv_cache.get()` miss and before issuing its own query. The reuse is scoped to the one batch and never persisted, so both security properties are untouched: the result still never reaches `osv_cache` (so no outage is recorded as a clean verdict for the TTL), and it is still `degraded`, so `authoritative` is still `False` and no dedup completion is recorded — a later observation of the same package still retries the lookup normally. Regression coverage: `test_degraded_prefetch_is_reused_instead_of_requeried_per_event`, which asserts the request count AND both security properties, so a future "optimisation" that caches the result to achieve the same request count fails it. The fixture was wrong, not the code; `_clean_response(n)` must always match the batch size.

Suppressing the CACHE write alone is not sufficient, and this is the half that is easy to miss: `_process_claimed_event()` records a dedup completion in `_processed_this_session`/`_cache_only_completions` for any `_process_event()` call that does not RAISE, and a degraded lookup does not raise — so the same install observed again was dropped at the claim step for the rest of the window (2h for a cache event, per `_CACHE_DEDUP_WINDOW_SECONDS`), never re-checked even after OSV recovered. Confirmed empirically with a dedupable cache event. `_process_event()` therefore now RETURNS `bool` — whether the OSV verdict was authoritative — and `_process_claimed_event()` records a completion only when it is `True`. Note the malicious branch's own early `return` must return `authoritative` (not a bare `return`), and any test stubbing `_process_event` must return `True`, or a falsy `None` silently disables the dedup layer for that test. Verify BOTH halves with a reproduction, since each is independently sufficient to lose the install: an outage must leave `osv_cache` empty for that key AND leave both dedup dicts empty, and the next observation after recovery must produce a real alert. Regression coverage: `test_osv_outage_is_not_cached_as_a_clean_result` and `test_degraded_lookup_does_not_record_a_dedup_completion`.

`pa scan-cache` (`_run_scan_cache()` in `cli/app.py`) is a SEPARATE, standalone caller of this same dual-classification behavior — it does NOT go through `daemon.py`'s dedup layer at all, since it never constructs a `Daemon` or calls `_claim_for_processing()`/`_process_claimed_event()`. Use that shared helper rather than a local rule: it dispatches to each ecosystem's own `normalise_name` (PEP 503 separator collapsing for PyPI, lowercase-only for npm so `socket.io` is NOT rewritten to `socket-io`) and never raises or propagates a plugin exception.

`_run_scan_cache()`'s own `poll_only_cache_paths()` try/except had the identical unvalidated-duck-typed-return bug the `_discover_dirs_by()` paragraph above documents for `cache.py` — the two are separate call sites with separate copies of this same isolation pattern, so the same class of bug had to be (and was) fixed independently in each. `cast("list[Path]", poll_only_fn())` is only a type-checker hint, not a runtime check, so a plugin returning `None` instead of raising survived the `try/except` unflagged and only failed later, unguarded, at `cache_dirs = cache_dirs + poll_only_dirs` (`TypeError`, list + None) — aborting the ENTIRE `scan-cache` command, not just this one language's scan, exactly the "must degrade to unavailable, not discard other languages' work" failure this try/except already exists to prevent for a RAISING hook (see this method's own comment above). If either call site's validation is changed, change the other the same way — nothing shares this logic between them, so a fix to one does not protect the other.

`classify_cache_file()`'s return needs a SHAPE check before ANY field is dereferenced, not just a type check on the fields themselves — and the two are separate bugs found a round apart. `_run_scan_cache()` validated `metadata.name`/`.ecosystem`/`.version` with `isinstance` (the paragraph below), but the guard that skips unversioned entries — `if not metadata or not metadata.version:` — ran BEFORE it, so a duck-typed plugin returning an object with no `version` attribute at all (not merely a wrong-typed one) raised `AttributeError` right there. Regression coverage: `test_run_scan_cache_skips_entry_with_non_metadata_shaped_return`, which also pins that a legitimate `version=None` entry is still skipped without a warning.

`classify_cache_file()`'s RETURN VALUE is the same class of hazard as those hooks' returns, and needs validating for the same reason: `PackageMetadata` is a plain dataclass with no validation, so a plugin can hand back a non-`str` `name`/`ecosystem`/`version` and the type annotation is only a type-checker hint. In `_run_scan_cache()` (`cli/app.py`) that escaped the per-entry `try/except` around the `classify_cache_file()` CALL itself, because the malformed value only blows up later: `normalise_package_name_for()` documents itself as never raising, but that contract holds only for a string — with a non-string the plugin's own `normalise_name` hook raises (caught and logged, as designed) and then the FALLBACK raises on the same value and escapes. Regression coverage: `test_run_scan_cache_skips_entry_with_malformed_metadata_types`.

Confirmed empirically. Fixed the identical way as the other two sites — validate inside the same `try`, raise `TypeError` on a malformed shape, let the existing `except Exception:` catch it and fall through to `_ERROR_DISPLAY`. The REQUIRED hooks — `cache_paths()` and `cache_file_globs()` — need exactly the same treatment, and were left unvalidated at two of those three sites long after the optional hook beside them was fixed. Both are duck-typed too, and their `try/except` caught a RAISE while trusting whatever a non-raising call RETURNED. In `_run_scan_cache()` that aborted the WHOLE `scan-cache` command, leaving every other language unscanned: `cache_paths() -> None` failed at `cache_dirs + poll_only_dirs` (TypeError), a non-`Path` element at `cache_dir.exists()` (AttributeError), and a non-`str` glob inside `cache_dir.glob()` (TypeError) — three of four malformed shapes confirmed empirically. Note the fourth (a bare `str` for globs) happened to survive via the pre-existing `if not globs: continue` falsy check, so testing only one shape would have suggested the hook was already safe. Regression coverage: `test_run_scan_cache_isolates_malformed_required_hook_returns` (parametrized over all four shapes), `test_languages_info_malformed_cache_paths_shows_error`, and `test_languages_info_valid_cache_paths_still_render` so the validation cannot over-trigger.
- `Daemon._processed_this_session`, keyed by `(ecosystem, package_name, version, project_path, occurrence)` — this is what makes the version-dir and `.whl` events (same project_path, since both come from the cache monitor) collapse into one evaluation, while still keeping two *different* projects installing the same version as separate alerts (deliberately: collapsing on `project_path` would let one project's clean copy mask another's independently-compromised copy of the same name/version, the same risk `scoring.py`'s own scan path explicitly guards against).
- `Daemon._cache_only_completions`, keyed by the narrower `(ecosystem, package_name, version, occurrence)` — no `project_path` — which additionally collapses two *separate* cache-monitor observations of the same version (e.g. a second, unrelated build) without ever suppressing a process-monitor event, since only a `source="cache"` completion is recorded there. This exists because `_resolve_package_dir()` returns no directories at all for a cache event (nothing has been extracted to disk yet), so a cache event's analysis is always weaker than a process event's — the full key alone would otherwise let a cache event that won a race permanently block the richer process observation of the very same install for the rest of the window.

The `occurrence` component (from `_occurrence_key()`) exists because `version` is not always a reliable install-occurrence discriminator, in TWO independent ways. First: `PackageEvent.version` is `None` for any unpinned install (`pip install requests`, no `==` — `parse_package_spec()`'s own docstring calls this out as deliberate, not an edge case), and with `version=None` two COMPLETELY INDEPENDENT installs of the same package in the same project (a reinstall after `pip uninstall`, or upgrading to a version released since the last install) used to share the exact same key and silently collapse into one evaluation — confirmed empirically. Second, and separately: even a RESOLVED `version` doesn't guarantee identical content for a process-backed event — a git/path/direct-URL-sourced dependency's uv.lock entry records its own DECLARED version (from its pyproject.toml), not a content hash, so a git ref moving forward or a local path dependency being rebuilt produces genuinely different content with no version bump at all (`_parse_uv_lock()` doesn't special-case a `source = {git = ...}`/`{path = ...}` entry — it's a plain `pkg.get("version")`). Two different processes reinstalling the SAME declared version at different commits/content used to collapse into one evaluation the same way — confirmed empirically, and the second install's tree never got heuristic scanning at all. `_occurrence_key()` therefore always returns `(event.pid, event.pid_create_time)` first, for ANY event (resolved or not) where both are available — this covers the common process-monitor case for both failure modes, and deliberately means two different processes installing the identical, genuinely immutable registry version (e.g. `requests==2.31.0`) are now ALSO evaluated separately; an occasional duplicate evaluation there is an accepted, comparatively cheap cost. Only when no pid is available AND `event.source == "cache"` does it fall back to `""` (a constant) if `version` is resolved — this is what still lets `classify_cache_file()`'s deliberate version-dir + `.whl` dual classification for the same uv sdist build collapse into one evaluation, since neither of those cache events ever carries a pid to differentiate them. A pid-less PROCESS event with a resolved version, or any event (cache or process) whose version is also `None`, gets `_UNDEDUPABLE` instead — `_UNDEDUPABLE` makes `_claim_for_processing()` skip the dicts entirely and always claim fresh, deliberately accepting an occasional duplicate alert over silently dropping a genuinely separate install with no way to tell it apart from the previous one.

The `""` constant fallback originally applied to ANY event with a resolved version and no pid, not just cache ones — this was itself a bug: a pid-less PROCESS event carries far more identity signal than a cache event even without a pid (a resolved `project_path`, a manager, a real invocation), so collapsing it onto the same source-blind constant a cache event uses reopened exactly the ambiguity the pid-first handling above exists to close, in two distinct, confirmed-empirically ways. First: two different PROCESS events for the SAME declared-version git/path reinstall (see the pid-first paragraph above), both with pid resolution unavailable, shared the same `(ecosystem, name, version, project_path, "")` key when they also shared `project_path` — the second reinstall's own, possibly different content silently never got its own evaluation. Second, more subtly: a process event's `project_path` is `None` too whenever `cwd` couldn't be read from `process_iter()` (see `ProcessMonitor._scan_processes()`'s own `cwd_str = info.get("cwd")` handling) — a pid-less process event with `project_path=None` then shared the exact SAME full key as an UNRELATED cache event for the same package/version, both having `project_path=None` and occurrence `""`. If the cache event won the race and got processed first, its completion entry in `Daemon._processed_this_session` silently marked the richer process event as already handled for the whole dedup window — `_resolve_package_dir()` deliberately returns no directories for a cache event (see its own paragraph below), so this meant source-code heuristic scanning was skipped entirely for a real install, not merely delayed. The fix scopes the `""` fallback to `event.source == "cache"` only; a pid-less process event now falls straight through to `_UNDEDUPABLE` and always gets its own fresh evaluation, at the cost of an occasional duplicate for the common, harmless "pid resolution glitched" case — the same "duplicate over silent miss" tradeoff this dedup layer makes everywhere else. If you touch this scoping again, re-verify both failure modes empirically: two pid-less process events sharing (name, version, project_path) must each be evaluated, and a pid-less process event must never be starved by an unrelated cache event even when both happen to have `project_path=None`.

`_occurrence_key()`'s `(event.pid, event.pid_create_time)`-first design only protects a process-backed event if `ProcessMonitor` actually carries those two values all the way onto the `PackageEvent` — and it only did so for the IMMEDIATE-parse path (a package named directly on the command line, e.g. `pip install flask`), not the DEFERRED, lockfile-scanning path (`_PendingInstall`/`_emit_from_lockfile()` in `monitors/process.py`) that most `uv sync`/`npm install`/`composer install` invocations with no package named on the command line actually take — arguably the MORE common case, not an edge case. `_PendingInstall` originally stored no pid at all, and `_emit_from_lockfile()`'s `PackageEvent` construction left `pid`/`pid_create_time` at their default `None` — so every deferred event silently fell through to `_occurrence_key()`'s resolved-version fallback (`""`) regardless of how many different processes produced it, exactly reopening the same-declared-version-different-content collapse the pid-first design exists to close (see the paragraph above), just for the deferred path specifically. Confirmed empirically. `_PendingInstall` now carries `pid`/`pid_create_time` (sampled at the same `process_iter()` snapshot as `event_pid`/`create_time` are for the immediate path, in `_scan_processes()`), and `_emit_from_lockfile()` puts them on its `PackageEvent` too. If `ProcessMonitor` ever grows a third code path that constructs a `PackageEvent`, thread pid/create_time through it the same way — this has now been missed once already for a path that isn't obscure.

Threading `pid`/`pid_create_time` onto the eventual `PackageEvent` isn't enough on its own, either: `ProcessMonitor`'s OWN internal bookkeeping for tracking a deferred install between detection and completion — `_seen_processes` (was `_seen_pids`), `_pending`, and `_scan_processes()`'s own `current_processes` snapshot (was `current_pids`) — must ALSO key by `(pid, create_time)`, not bare `pid`. A pid is only a stable identifier for the specific process instance it was observed on WHILE that exact process stays alive; Linux allocates PIDs sequentially with wraparound (not handed back out the moment they free up — see `ProcessMonitor.__init__`'s own comment), so reuse of any specific pid is rare in practice, but bare-pid bookkeeping would still get it silently wrong on the rare occasion it does happen. Two distinct, confirmed-empirically failure modes from this: (1) the reused pid's OWN new process gets silently skipped by `if pid in self._seen_pids: continue` before `_try_parse()` is ever reached, since that pid number is already marked seen from the finished process — its install is missed entirely, not just misattributed; (2) `finished = self._pending.keys() - current_pids` never recognises the ORIGINAL process's pending install as finished, since its pid number still "looks" present in the next `current_pids` snapshot (it's technically there — as the unrelated new process) — the pending install is stuck in `_pending` indefinitely, delaying (or, if that pid is never freed again in a way the daemon observes, permanently blocking) its lockfile scan. `create_time` can be `None` for a pid whose `create_time` attribute specifically failed to read this one poll (see `_scan_processes()`'s own per-attribute-failure comment) — such a pid needs SOME identity for this internal bookkeeping, and reconciles onto whatever identity that same pid was already tracked under from an earlier poll rather than forming a bare `(pid, None)` from scratch (see the next paragraph for why).

`process_identity = (pid, create_time)` being formed FRESH from only this poll's `create_time` reading, with no reconciliation against this same pid's identity on a PRIOR poll, was itself still a bug even after the `(pid, create_time)`-keying fix above: `create_time`'s per-attribute read failure (see two paragraphs up) is transient and can flip between polls for a process that never actually exited — `None` this poll, a real value on the previous and/or a later one, or vice versa. A deferred install already tracked in `_pending` as `(pid, real_create_time)` gets a `(pid, None)` sibling the moment `create_time` next reads as `None` for that same still-running pid — `(pid, real_create_time)` then no longer appears in that poll's `current_processes` (only `(pid, None)` does), so `finished = self._pending.keys() - current_processes` wrongly includes it and `_emit_from_lockfile()` fires while the installer is still running, not finished — confirmed empirically. The same flip in the other direction (a pid first seen with `create_time=None`, then reading as real on a later poll for the same still-running process) reparses and re-emits an already-seen immediate install's cmdline a second time — also confirmed empirically.

`_scan_processes()` builds `known_create_time_by_pid` — a `pid -> create_time` map (`create_time` here can itself be `None`) from `_pending`'s and `_seen_processes`' keys, snapshotted at the START of the poll before any of them are mutated — and reconciles `process_identity` onto the PRIOR poll's recorded reading for a pid ONLY when THIS poll's read failed (`real -> None`) — the reverse (`None -> real`) deliberately forms a distinct identity, since collapsing it overwrites a replacement process's own readable `create_time` and hides genuine PID reuse (see the one-directional paragraph below); `event_pid` is likewise recomputed off the reconciled `create_time`, not the raw per-poll reading, so it stays consistent with `process_identity`. If `create_time` is a real, present value on BOTH the prior and current poll but they DISAGREE (e.g. `100.0` then `999.0`), that is exactly what genuine PID reuse looks like, and must keep forming a distinct identity so the original pending install is still correctly recognised as finished and the new process is still tracked in its own right — collapsing that case too would silently reintroduce the PID-reuse bug the `(pid, create_time)`-keying fix above exists to close.

Reconciliation is ONE-directional — only when THIS poll's `create_time` read failed (`real -> None`). The reverse (`None -> real`) was tried and is a confirmed SILENT MISS: it overwrote a replacement process's own perfectly readable `create_time` with `None`, so its identity collapsed onto the previous process's `(pid, None)` entry in `_seen_processes`, the `if process_identity in self._seen_processes` guard matched, and its install was skipped entirely. Confirmed empirically (a pid first seen with an unreadable create_time, then reused by a different install whose read worked, emitted no event at all). That is strictly broader than the residual risk below, which additionally needs the REPLACEMENT's own read to fail.

One-directional reconciliation has a consequence for the DEFERRED path that the identity change alone does not handle: the reverse flip (first sighted as `(pid, None)`, now readable) deliberately forms a NEW identity — that is exactly what keeps PID reuse detectable — but any `_pending` entry already tracked under the old `(pid, None)` key was left behind. It then no longer appears in that poll's `current_processes`, so `finished = self._pending.keys() - current_processes` treated it as exited and ran `_emit_from_lockfile()` while the installer was STILL RUNNING and possibly still writing the lock file. Confirmed empirically: a real `uv.lock` was scanned and its package emitted one poll after the create_time became readable, with the process still alive — and, because the entry was then re-added under the new identity, the same install was emitted a SECOND time when the process genuinely exited. `_scan_processes()` therefore migrates the entry (`self._pending[process_identity] = self._pending.pop((pid, None))`) whenever the current reading is real and a `(pid, None)` entry exists. Only ever FROM a `None` prior reading: two real values that DISAGREE are precisely what PID reuse looks like, and must keep the old entry so it is still correctly recognised as finished. Verify all three directions with a reproduction: no emission while the process is still running, exactly one emission once it genuinely exits (carrying the reconciled `create_time`), and a genuine two-real-values PID reuse still emitting the ORIGINAL process's pending install. That migration must refresh the entry's OWN `pid`/`pid_create_time`, not just move the dict key: `_emit_from_lockfile()` builds its `PackageEvent` from those fields on the `_PendingInstall` object, which still held the `None` readings from the poll it was first tracked on. In the common case this is invisible — the new identity isn't in `_seen_processes`, so the same loop iteration re-parses and REBUILDS the entry with fresh values a few lines further down — but several `continue` guards sit between the migration and that rebuild. A poll where `create_time` recovers while a DIFFERENT attribute fails (an empty `cmdline`, say: the same per-attribute read failure on another field) migrates the entry and never reaches the rebuild, so it emitted a pid-less event on exit and `_occurrence_key()` fell back to a constant that cannot tell two separate installs of the same declared version apart. Confirmed empirically. Note the review finding that raised this described it as unconditional and as failing `test_deferred_install_still_emitted_once_the_process_exits`; that test passed throughout, because the rebuild covers the straightforward case — the bug is real but reachable only through the skipped-rebuild path, which is why a reproduction has to fail a second attribute on the recovery poll. Regression coverage: `test_migrated_pending_entry_carries_the_recovered_pid`.

That migration must be CORRELATED ON CWD, not unconditional — an unconditional one introduced a silent miss of its own. "A pending `(pid, None)` whose create_time is now readable" describes two indistinguishable situations: the same process recovering (what the migration is for) and a DIFFERENT installer reusing that pid. On reuse, the migration moves the old entry onto the new identity and the parsing block further down then assigns the NEW install to that very key, overwriting the old one — whose install is then never emitted at all. Confirmed empirically (two deferred installs sharing a pid, only the second reported; without the migration both were). That is strictly worse than the duplicate the migration prevents, and it exceeds the residual risk documented above, which additionally requires the replacement's own create_time read to fail. The same process keeps the cwd its pending install was recorded with, so the migration now requires `str(pending.cwd) == info.get("cwd")`; an uncorrelated pair is left alone, keeping its `(pid, None)` key and still being recognised as finished exactly as before the migration existed. Verify BOTH directions: a same-process create_time recovery must still migrate (or the premature/duplicate emission returns), and a pid reused by an installer in a DIFFERENT directory must emit both installs. Regression coverage: `test_pid_reuse_does_not_overwrite_an_earlier_pending_install`; note disabling the migration outright still fails three other tests, which is what keeps it honest that the correlation narrowed it rather than neutering it.

Note a fixture for any of these MUST create a real lock file — `_emit_from_lockfile()` silently no-ops without one, so a test that omits it passes on an empty queue even while the premature scan is happening, which is exactly how this went unnoticed. Regression coverage: `test_deferred_install_not_emitted_when_create_time_becomes_readable` and `test_deferred_install_still_emitted_once_the_process_exits`.

The two cases are genuinely indistinguishable from the available data: "same process, read recovered" and "pid reused, replacement readable" both present as (prior `None`, now a real value), and telling them apart would require exactly the value that failed to read. So this is a security-vs-noise trade-off, and it is resolved the way the rest of this module resolves them — a duplicate alert over a silent miss. An earlier round reverted one-directional reconciliation on the grounds that it caused a GUARANTEED duplicate `_pending` entry and duplicate lockfile scan on every ordinary create_time glitch; that cost was re-measured and does not occur — a `readable -> glitch -> readable` cycle keeps exactly ONE pending entry and triggers no extra scan, because the `real -> None` direction (which is retained) already covers the common glitch. Only a pid whose VERY FIRST sighting had an unreadable create_time pays a duplicate when it later becomes readable.

The residual risk that remains: a pid reused AND the new process's create_time also failing to read on that exact poll still reconciles onto the old identity, and that install can be missed. That needs both rare conditions together — PIDs are allocated sequentially with wraparound on Linux, not handed back out eagerly (confirmed by sampling `ps -ef` across many short-lived processes: PIDs climb forward through a large free range) — and is accepted, not ruled out. Regression coverage: `test_scan_processes_detects_pid_reuse_after_unreadable_create_time`.
A pid that both gets reused by an unrelated process AND has that new process's own `create_time` fail to read on its very first sampled poll — the exact conjunction the symmetric reconciliation above accepts as a residual risk — is not distinguishable from an ordinary readability flip of the SAME still-running process; a fresh, separate `psutil.Process(pid).create_time()` call to re-verify isn't a safe alternative either, since a create_time read made any later than the originating `process_iter()` snapshot can itself observe a still-further-reused process (see that snapshot's own comment on `event_pid`/`create_time`). This is accepted, not fixed, given how rare the underlying PID reuse is in the first place on Linux's actual allocation behavior.

The `_UNDEDUPABLE` branch in `_process_claimed_event()` (originally in the single, unsplit `_process_event_deduped()` this was later split out of — see below) must still wrap its `_process_event()` call in the same `try/except Exception: log.exception(...)` the dict-tracked path below it uses — it was initially added unguarded, on the reasoning that "no dict bookkeeping happens here anyway," but that's a separate concern from failure isolation: `Daemon._consume()` awaits this method directly inside its own `events()` loop with no surrounding try/except of its own, relying entirely on it to contain a failure to one event. An unhandled exception from a transient OSV/database/plugin failure while processing an `_UNDEDUPABLE` event therefore propagated straight out of `_consume()` and permanently killed that monitor's whole consumer task — confirmed empirically: a second, later event from the same monitor was never processed after the first one's failure, for the rest of the daemon's uptime. If you add a fourth branch to this method, or restructure the existing ones, keep every path that calls `_process_event()` wrapped the same way — "this branch skips the dedup bookkeeping" must never imply "this branch also skips failure isolation."

`_process_event_deduped()` no longer exists as a single method — it was split into `_claim_for_processing()` (the check/wait/claim decision, returning whether this call now owns the key) and `_process_claimed_event()` (running `_process_event()` for an already-claimed event and recording completion), specifically so `_consume()` could call the CLAIM step for every event in a batch BEFORE calling `_batch_prefetch()` for that batch, not just before `_process_event()`. `_batch_prefetch()` issues a real OSV `querybatch` network call for any event `osv_cache` doesn't already have; when the claim only happened inside the old, unsplit method (i.e., AFTER `_batch_prefetch()` had already run for the whole batch), two concurrent `_consume()` tasks (one per monitor) that both observed the SAME uncached install could each independently issue their own OSV request for it before either had claimed `self._in_flight` — only the later risk-PROCESSING step was actually deduplicated, not the network call — confirmed empirically (two identical `querybatch` requests for one install). `_consume()` now: (1) claims every event in the deduped batch via `_claim_batch_without_deadlock()` (see its own paragraph below — NOT a plain loop over `_claim_for_processing()`, which has its own deadlock problem for a multi-key batch), keeping only the ones this call won; (2) prefetches OSV results for just the claimed subset; (3) processes each claimed event via `_process_claimed_event()`. Splitting this way introduced a genuine new failure mode that had to be handled explicitly: `_batch_prefetch()` has no try/except of its own, and by step 2 every claimed event already holds a live `self._in_flight` entry — an unhandled `_batch_prefetch()` exception would leave those claims stuck forever, permanently deadlocking any OTHER task's `await in_flight_event.wait()` for the same key (confirmed empirically: without an explicit release, two concurrent tasks for the same install hung the whole `asyncio.gather()` over them). `_consume()` therefore wraps its `_batch_prefetch()` call in its own `try/except` — but, having learned from the next paragraph's bug, does NOT release every claim and abandon the batch on failure; it logs and falls straight through to processing every claimed event as normal, exactly as if `_batch_prefetch()` had found nothing to prefetch.

An earlier version of that `_batch_prefetch()` failure handling — release every claim via `_release_claim()`, then `continue`, skipping the rest of the batch entirely — fixed the deadlock above but introduced its own, separate and more serious bug: releasing `self._in_flight` only helps a DIFFERENT, concurrent task that happens to be waiting on the exact same key (the two-monitor scenario the deadlock fix's own test models). For the ordinary case — one observation of an install, no concurrent duplicate anywhere — nothing else holds a reference to these events once `continue` skips `_process_claimed_event()` for all of them: the install was silently and PERMANENTLY lost, with no `store_alert()` row, no retry, and no log signal beyond one generic exception naming the batch — confirmed empirically (a malicious package produced zero alert rows). The fix rests on `_batch_prefetch()` being purely a cache-warming OPTIMIZATION, not the only path that can reach OSV: `_process_event()` has its own independent `osv_cache.get()`/`osv_client.batch_query()` fallback, already wrapped by `_process_claimed_event()`'s own `try/except` (which correctly records no completion on failure, so a later occurrence of the same key can still retry it) — so a failed prefetch just means that per-event fallback runs unwarmed instead of hitting a warm cache, never a reason to skip processing outright. `_consume()`'s `_batch_prefetch()` failure handling now logs (naming every package in the abandoned prefetch, for visibility a bare `log.exception()` alone didn't give) and falls through to the same `for e in claimed: await self._process_claimed_event(...)` loop it would run on prefetch success, keeping every claim intact rather than releasing them. If you ever touch this again, re-verify with a SINGLE-observation reproduction (not just the two-monitor one that only proves no deadlock) that a persistent prefetch failure still results in the install being evaluated and, if malicious, alerted.

Claiming a BATCH of more than one key by simply looping `for e in batch: await self._claim_for_processing(e)` — which `_consume()` originally did after the split above — has its own, separate deadlock, independent of the `_batch_prefetch()`-failure one two paragraphs up. `_claim_for_processing()` BLOCKS (`await in_flight_event.wait()`) when a key is already `in_flight` elsewhere — and it does so WHILE THIS TASK STILL HOLDS every claim it made earlier in the same loop pass, since nothing releases them before the block. Two concurrent `_consume()` tasks whose batches happen to contain the SAME two keys in OPPOSITE order (task 1: `[A, B]`, task 2: `[B, A]`) can each claim their first key, then each block trying to claim their second key — which the OTHER task now owns and will never release, because that other task is itself blocked the exact same way. A classic circular-wait deadlock, confirmed empirically: neither task's `asyncio.gather()` over them ever returned. This is a real, not merely theoretical, scenario — a lockfile scan (`_emit_from_lockfile()` in `monitors/process.py`) and a cache-monitor sdist build backfill can each independently enqueue multiple packages that land in one `drain()`-produced batch (see `_consume()`'s own batch-assembly comment), and two such batches sharing packages in different orders is not exotic.

The fix splits the single-event claim decision into a non-blocking primitive, `_try_claim_once()` — the same per-key logic `_claim_for_processing()` used to inline directly, minus its own `while True: await ...; continue` retry loop — returning `True` (claimed), `False` (confirmed duplicate, drop it), or the contested `asyncio.Event` itself (never awaits). `_claim_batch_without_deadlock()` uses this to attempt every event in a batch in one pass; if any is contested, it releases EVERY claim this pass already made (via `_release_claim()`) BEFORE awaiting the contested key's Event, so this task holds nothing while blocked — breaking the circular-wait condition, since the other task's own blocked claim, if any, can now proceed. Once the wait resolves, it retries the WHOLE batch from scratch (not just the contested key), deliberately: by then this task's earlier claims may already be stale — e.g. `self._processed_this_session` may now carry a completion another task recorded for one of them while this task was waiting — and `_try_claim_once()` re-evaluates that correctly on retry, whereas resuming with the old claims would not. `_claim_for_processing()` itself still exists, now implemented as a loop over `_try_claim_once()`, and remains safe to call directly for a SINGLE event (its one remaining direct caller is a dedup-pruning test) — its blocking wait never holds any OTHER claim while it waits, so looping it is only unsafe for a genuine multi-key batch, not for one key at a time. If you ever add a THIRD way of claiming multiple keys at once, route it through `_claim_batch_without_deadlock()` (or the same release-before-wait pattern) rather than looping `_claim_for_processing()` — that loop shape has now caused this exact deadlock once already.

Both dicts are bounded by time, not a permanent per-session membership set, since a cache event's `project_path=None` would otherwise make a genuinely later, separate reinstall of the same version indistinguishable from a duplicate for the daemon's entire uptime — but the window is NOT the same for every event. A process-sourced event uses `_DEDUP_WINDOW_SECONDS` (300s, matching `_SITE_PACKAGES_WATCH_IDLE_SECONDS`'s own "how slow can a real install take" reasoning in `cache.py` — a slow dependency RESOLVER). A cache-sourced event uses the much longer `_CACHE_DEDUP_WINDOW_SECONDS` (2 hours) instead: the version-dir and `.whl` events this dedup exists to collapse (see the paragraph above) are emitted at the START and END of an sdist BUILD, not a resolver step, and a native extension requiring real compilation is not bounded by 300s the way a resolver is — this codebase's own `_is_idle_expired()`/`_prune_dead_owners()` site-packages watch logic (`cache.py`) already treats an install exceeding that SAME 300s idle timeout as legitimate, still-in-progress work, for exactly this reason. Using the short window for a cache event let the version-dir entry expire before a genuinely slow build's wheel event arrived, so the wheel was processed as a brand-new install — a real second `store_alert()` row and notification for one build, not just an internal duplicate — confirmed empirically. A cache event never carries a pid (see `_occurrence_key()`), so there is no owning-process-liveness signal available to keep the entry alive for precisely as long as the build runs, the way the site-packages watch does; a generously long fixed window is the deliberate, simpler alternative to threading a build/revision identity through `PackageEvent` to correlate the two events exactly — accepted as adequate for how long a real build can realistically take, not as an exact guarantee. `_claim_for_processing()` picks the window from `e.source`; `_dedup_pruning_loop()` has to work it out per-entry instead, since a `_processed_this_session` key doesn't carry `source` directly — it treats an entry as cache-sourced if its `(ecosystem, name, version, occurrence)` (the key with `project_path` dropped) is present in `_cache_only_completions`, which is written ONLY for cache events; that check must happen before deciding to prune, and stays valid because `_cache_only_completions` always uses the LONGER window and so can't have been pruned first for a still-live entry. A stale entry is also pruned proactively by `Daemon._dedup_pruning_loop()` (a background task started alongside `_update_check_loop()`/`_scheduler_loop()` in `Daemon._run()`), not just lazily when that exact key recurs — without it, a package version installed exactly once over the daemon's whole lifetime would leave its entry in memory forever, up to `_CACHE_DEDUP_WINDOW_SECONDS` late for a cache-sourced one.

`_consume()` has its OWN, separate dedup step — the batch-local `seen` filter that runs BEFORE any event in a batch reaches `_claim_for_processing()` at all (needed because a lock file scan can emit the same transitive dependency once per dependent package). This filter must fold in `_occurrence_key()` too, exactly like `_processed_this_session`/`_cache_only_completions` do — it used to key only on `(ecosystem, package_name, version, project_path)`, so two independent unpinned installs of the same package/project (different pid/`pid_create_time`) that happened to be drained into the SAME batch (e.g. two concurrent `pip install requests` runs both already queued by the time `_consume()` calls `monitor.drain()`) collapsed into one right there — confirmed empirically — before `_claim_for_processing()`'s own occurrence handling downstream ever got a chance to tell them apart, since by then only one of the two events still existed to be evaluated. An `_UNDEDUPABLE` event must never be deduplicated by this filter either, for the same reason `_claim_for_processing()` skips its own dicts for one: guessing an occurrence identity that doesn't exist is worse than an occasional duplicate alert. If you ever add a third dedup point anywhere in this pipeline, give it the same occurrence-aware key rather than a plain `(ecosystem, name, version, project_path)` tuple — that shape has now caused this exact silent-collapse bug twice, once per dedup point that had it.

If either the version-dir classification, `_processed_this_session`, `_cache_only_completions`, `_occurrence_key()`, or `_dedup_pruning_loop()` is ever changed, re-verify the whole chain still prevents a real double-alert (two `store_alert()` rows and two notifications for one install) without reintroducing any of the now-fixed regressions above — `store_alert()` itself has no uniqueness constraint to catch this at the DB layer.
